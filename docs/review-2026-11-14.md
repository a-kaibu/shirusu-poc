## 16GB 確保失敗の経路

16GB の確保失敗は記録中の Host ではなく、記録後に走らせた `shirusu inspect` で起きている。コミット 8cc0ad8 のメッセージに「inspect が全イベントを読み込む（16 GB allocation）」とあり、コードでも裏づけが取れた。

- `load_trace` はファイル全体を `std::fs::read` で読み、`read_trace` で全イベントを `TraceEvent` にする（`crates/shirusu-cli/src/main.rs:306-320`）。
- その上で `TraceView::build` が 1 イベントにつき 1 個の `EventView` を `Vec` に積む（`crates/shirusu-analysis/src/view.rs:680-693`）。
- `EventView` は 240 バイトなので、`Vec` が 2^26 要素へ倍増する瞬間に 16,106,127,360 バイトを要求する。これは約 3,355 万イベントを超えた時点で、無制限の持続負荷（約 7,500 万イベント）なら必ず通る。

CI は inspect を呼ばないよう回避しただけで、原因は残っている。同じ読み方をするのは `inspect`、`coverage`、`export`、`repair`、`shirusu-compare`、`shirusu-conformance`、`shirusu-test`、`shirusu-probe`。ストリーム読みの `TraceStream` は `dump` だけが使っている。

Host の記録経路は別に調べた。変換待ちキューは 256MB の予算で頭打ちになり、16GB に届く確保は見つからなかった。ただし長時間の記録では Index が増え続ける（P1-2）。

## P1 の詳細

### P1-1 同時に 9 本以上のスレッドが API を呼ぶと、9 本目以降は一切記録されず、Host からも見えない

- 軸: 堅牢性、性能。確度: 高（コードで確認）。
- 根拠: CLI は `LaunchConfig::new` の既定値をそのまま使い、Ring は 8 本固定（`crates/shirusu-host/src/recorder_launch.rs:63`、`crates/shirusu-cli/src/capture.rs:460`）。CLI に本数を変えるオプションはない。Agent DLL は Bootstrap で受け取った Mapping だけで動き、低水位時の Mapping 追加（`ExpansionService`、`spawn_expansion_manager`）はテスト以外から呼ばれていない。
- 起きること: 9 本目のスレッドは Slot を取れず、全呼び出しが NoSlot になる。件数は Agent 内のカウンタに残るだけで、Host は Trace に注記を足すが完全性は下げない（`crates/shirusu-host/src/recorder.rs:926-931`）。ブラウザや .NET アプリのようにスレッドが数十本あるアプリでは、Capture Coverage が Complete のまま大半のスレッドが欠ける。
- 性能面: Slot を取れなかったスレッドは登録キャッシュに入らないため、API を呼ぶたびに `register_thread` を通る（`crates/shirusu-hook/src/runtime.rs:1394-1411`）。毎回、共有 Mutex、Slot 取得の再試行、全スレッドの終了確認、回収待ち Mutex を踏む。記録されないスレッドが最も遅くなり、他スレッドとも競合する。
- 設計文書は「Slot 不足は Coverage の欠落とし、Host の非同期拡張を優先する」としている（`docs/spec-transport.md:181`）。部品はあるが実 Capture に結線されていない状態。

### P1-2 長時間の記録は最後の Index 書き込みで失敗し、Finalization のない Trace になる

- 軸: 安定度、省メモリ。確度: コード経路は高、到達時間は中。
- 根拠: Writer は Block を書くたびに `IndexEntry` を積み、上限がない（`crates/shirusu-trace/src/writer.rs:645`）。`finish` は Index を複製して 1 個の Block に符号化するが、`write_block` は 256MiB を超える Block を拒否する（`writer.rs:434-438`、`writer.rs:613`）。1 件は約 15 バイトなので、約 1,700 万 Block で `finish` が失敗する。
- Block が増える速さ: 変換ワーカーは「疎な流れを遅らせない」方針で、回収 1 回分をそのまま 1 Block にする（`crates/shirusu-host/src/trace_pipeline.rs:231-235`）。Host は待機中だと公開 1 回ごとに起きるため、まばらに呼ぶスレッドが数本あるだけで毎秒数千 Block になる。毎秒 3,000 Block なら約 95 分で上限に届く。
- 結果: 何時間分のイベントはディスクにあるのに、Index と Finalization が書かれず「capture failed」で終わる。失敗は最後まで分からない。直前のメモリは Index 本体、複製、符号化バッファで約 1.1GB。
- 小さい Block の副作用: 1 Block ごとに 32 バイトのヘッダー、Batch ヘッダー、個別の zstd フレームが付き、`File` へ直接 2 回 write する（`writer.rs:650-651`、`recorder.rs:490`）。Trace の肥大と syscall 数の両方に効く。

### P1-3 Reader の既定上限のせいで、正常な長い Trace を全ツールが「破損」として読み止める

- 軸: 堅牢性。確度: 高。
- 根拠: 既定上限は Block 100 万個、展開後 1GiB、Blob 512MiB（`crates/shirusu-trace/src/reader.rs:36-45`）。CLI、compare、conformance、test、probe のどれも既定値のまま使う。`docs/trace-format.md:731-734` は「設定で変更可能にする」としているが設定はない。
- 到達の早さ: P1-2 の速さなら Block 100 万個は数分。高負荷なら展開後 1GiB は 1 分前後。
- 起きること: `inspect` と `coverage` は Finalization まで読めず、完全な Trace を「不完全、Event Integrity を失った」と報告して終了コード 1 を返す（`crates/shirusu-analysis/src/view.rs:660-669`）。`dump` は `stream.finish()` も issue も見ないため、上限で黙って出力を止めて終了コード 0（`crates/shirusu-cli/src/dump_export.rs:94-144`）。`repair` は先頭部分だけの Trace を「lost 0」で書き出す。
- 記録は成功しているのに、検証側が誤って失敗と判定する形になる。

### P1-4 解析ツールが Trace 全体を何重にもメモリへ載せる

- 軸: 省メモリ。確度: 高。経路は上の「16GB 確保失敗の経路」のとおり。
- 補足: `EventView::of` はイベントごとに API 名と Schema 名の `String`、型の `Vec`、各フィールド名を複製する。`max_events` の既定 1 億は `TraceEvent` だけで 12.8GB を許すので、上限は歯止めになっていない。
- `dump` も入力はストリームだが、一致したイベントを全部 `Vec` に溜めてから出力する（`dump_export.rs:96-131`）。`--limit` なし、または `--order=global` では同じ問題になる。

### P1-5 `capture` と `attach` に、利用者が記録を止める手段がない

- 軸: 安定度。確度: コード経路は高、Ctrl-C 時の挙動は Windows 実機未確認。
- 根拠: 回収ループは対象プロセスの終了でしか抜けない（`recorder_launch.rs:206-237`）。`crates/` に `SetConsoleCtrlHandler` はない。
- 起きること: 常駐プロセスへの attach や GUI アプリの記録は、対象を終了させるか Host を Ctrl-C で落とすしかない。Ctrl-C なら Index と Finalization が書かれず、キューに残った最大 256MB 分が失われ、Agent の終了手順も走らない。attach した対象はフックが入ったまま Host を失う。

### P1-6 WndProc の差し替えで、Windows が返す不透明なハンドルを関数として呼ぶ

- 軸: 堅牢性（対象プロセスのクラッシュ）。確度: 中。Windows 実機未確認。
- 根拠: ラップするかどうかの判定は `n_index == GWLP_WNDPROC && new_proc != 0` だけ（`crates/shirusu-hook/src/engine/callbacks.rs:383-394`）。ラッパーは保存した値を関数ポインタとして直接呼ぶ（`callbacks.rs:210,250`）。
- 起きる条件: ANSI と Unicode が食い違うウィンドウでは、`GetWindowLongPtr` と `SetWindowLongPtr` は関数アドレスではなく `CallWindowProc` 用のハンドルを返す。アプリがサブクラス化を解除するためにその値を `SetWindowLongPtr` へ戻すと、Agent はハンドルを「元の手続き」として保存し、次のメッセージでそこへジャンプする。記録なしなら Windows がハンドルを解決するので落ちない。
- 古い ANSI アプリがコモンコントロールをサブクラス化する場面で起こり得る。実機での再現確認が要る。

### P1-7 WndProc、COM、WinRT のイベントは 1 回ごとに Schema を作り直して BLAKE3 を計算する

- 軸: 性能。確度: 高。
- 根拠: `encode_callback_enter` は呼ばれるたびに `callback_enter_schema()` を作る（`crates/shirusu-hook/src/callback.rs:121-131`）。フィールド名の `String` を並べ、`make_schema` が内容ハッシュを計算し、使うのは型の並びだけ。COM と WinRT も同じ形（`com.rs:433-438`、`com.rs:506-514`、`winrt.rs:614-624`）。
- 1 呼び出しで Schema 構築 2 回、ハッシュ 2 回、ヒープ確保 15〜25 回。その確保自体がフック済みの HeapAlloc を通る。これらの経路は生成 API が使う Hazard の高速経路も使わず、`Arc` の複製と共有カウンタ更新が入る。
- GUI アプリは毎秒数千のメッセージを処理し、COM の AddRef と Release はさらに多い。型の並びを静的に持てば消える費用。

## P2 の詳細

### P2-1 複数スレッドが動くだけで「Host が遅れている」と判定され、無圧縮で書かれる

- 軸: 省メモリ（ディスク）、性能。確度: コードは高、実際の発生率は未計測。
- 根拠: 変換ワーカーは、次のコマンドが既にキューにあれば `backlogged` とみなして無圧縮で書く（`crates/shirusu-host/src/trace_pipeline.rs:275-288`）。ところが回収側は 1 回の poll で動いている Ring の数だけコマンドを続けて送る。別スレッドのコマンドは結合できず `pending` に残るので、2 本以上のスレッドが同じ poll に入れば負荷が軽くても条件が成立する。
- 結果: マルチスレッドの対象では圧縮がほぼ効かず、文書の数値で約 4.7 倍のファイルになる。ディスクが遅い環境では書き込み量の増加が遅れを増やす。遅れの判定はキューのバイト数や滞留時間で見るほうが実態に合う。

### P2-2 呼び出し元の分類が、全スレッド共有の RwLock を呼び出しごとに取る

- 軸: 性能（スレッド数に対する伸び）。確度: コードは高、効果の大きさは未計測。
- 根拠: Inline Hook の入口スタブを通った呼び出しはすべて `classify_caller` を呼び、`CACHE.read()` を取る（`crates/shirusu-hook/src/caller.rs:425-433`、呼び出し元は `engine/file_io.rs:142`）。読みロックでも共有キャッシュラインへの書き込みが 2 回入る。
- この経路を最も多く通るのは、記録しない Windows 内部からの呼び出し（Windows DLL 内の HeapAlloc など）。Runtime 参照や Call ID で共有書き込みを削った設計と逆向きになっている。スレッドごとに直前の範囲を覚えればロックなしで済む。
- 関連: JIT など非イメージの呼び出し元は確保領域ごとに Unknown として登録され、DLL のアンロードでしか消えない（`caller.rs:377-386`）。JIT が領域を作り直すアプリでは表が増え続け、挿入は毎回配列をずらす。

### P2-3 欠落記録がセッション終了までメモリに溜まり、Trace の末尾にまとめて書かれる

- 軸: 省メモリ、堅牢性。確度: 高。
- 根拠: `DrainWorker.loss_events` は欠落のあった回収ごとに 1〜2 件増え、書き出すのは停止時と Ring の引退時だけ（`crates/shirusu-host/src/lib.rs:806-838`、`recorder.rs:410`、`recorder.rs:892`）。終了しない呼び出しを追う `open_calls` も同じく増える（`lib.rs:564`）。
- 結果: 過負荷が続くセッションでは時間に比例してメモリが増える。欠落記録は Trace 上で起きた位置に置かれず、Host が異常終了すると全部失われる。その場合、残った Trace からは欠落があったことすら分からない。

### P2-4 スレッドの生成と終了が多いと、正常な Slot 再利用で Integrity Lost になり得る

- 軸: 安定度。確度: 中（競合の窓はコードで確認、発生率は未計測）。
- 根拠: Agent は Slot を再利用するとき Control を非アトミックに 0 へ戻す（`crates/shirusu-transport/src/layout.rs:160-194`）。Host の回収側が古い読み位置を持ったまま読むと、書き位置が読み位置より小さく見えてその Ring を停止し、Integrity Lost にする（`crates/shirusu-host/src/lib.rs:452-460`）。`recorder.rs:759-766` のコメントも fail-closed であることを認めている。
- 関連: Ring の引退処理は変換キューが空になるまで待つ（`recorder.rs:404`）。その間、最大 256MB 分の変換が終わるまで全 Ring の回収が止まり、スレッド終了が欠落の引き金になる。

### P2-5 手書きの ReadFile と WriteFile が、同期呼び出しでもプロセス共通の Mutex を取る

- 軸: 性能。確度: 高。
- 根拠: `begin_pending_overlapped` は OVERLAPPED が NULL でも無条件に呼ばれる（`crates/shirusu-hook/src/engine/file_io.rs:376-387`）。登録はアドレス 0 で早期に戻るが、`PendingSubmission` の Drop が呼ぶ `cancel` は 0 を見ずに Mutex を取る（`capture.rs:405-441`）。
- 同じ経路には `Arc` の複製 2 回、共有カウンタ更新、`Vec` 確保 4 回以上、`ReadProcessMemory` 2 回以上がある。文字列引数は 64 バイトずつ syscall で読むため、260 文字のパスで 9 回になる（`capture.rs:100-147`）。ファイル I/O が多いアプリで最も呼ばれる API が最も遅い経路にいる。

### P2-6 COM 追跡表が増え続け、QueryInterface(IUnknown) のたびに全件を走査する

- 軸: 省メモリ、性能、長時間安定度。確度: コードは高。
- エントリは削除されず、パッチ済みの Release で 0 になったときに `destroyed` 印が付くだけ（`crates/shirusu-hook/src/com.rs:694-698`）。
- `note_query_interface` は IUnknown のとき、グローバル Mutex を持ったまま表全体を回す（`com.rs:772-782`）。総作業量が二次になり、COM を使う全スレッドが 1 本の Mutex に並ぶ。
- `intercept_object` の早期リターンは `intercepted` を見るが、標準の経路が立てるのは `iunknown_intercepted`（`engine/com_install.rs:403`、`com.rs:655-657`）。そのため既知オブジェクトでも QI のたびに設置処理（`VirtualQuery` 3 回、`ReadProcessMemory` 4 回）をやり直す。単純な取り違えに見える。

### P2-7 完了待ちの非同期 I/O 登録が残り、別の操作の完了を古い呼び出しの完了として記録する

- 軸: 堅牢性（誤った記録）、省メモリ。確度: 仕組みは中〜高、頻度はアプリ次第。
- 登録を消すのは GetOverlappedResult と GetQueuedCompletionStatus の Detour だけ（`engine/file_io.rs:668-678`、`file_io.rs:772-778`）。GetQueuedCompletionStatusEx、スレッドプール I/O、イベント待ちで完了する操作は残る。
- 照合は OVERLAPPED のアドレスだけ。残ったアドレスが別の操作（DeviceIoControl、ConnectNamedPipe など）で再利用されると、古い call\_id の `CallCompleted` が新しい操作のバイト数と、古いバッファアドレスの現在の中身で記録される。

### P2-8 全スレッド停止が 1 本の失敗で全体を中止し、再試行しない

- 軸: 安定度。確度: コードは高、実際の頻度は中。Windows 実機未確認。
- Toolhelp の一覧を取った後に終了したスレッドが 1 本あると `OpenThread` が失敗し、その回の設置が丸ごと `thread-suspend-failed` になる（`crates/shirusu-hook/src/engine/inline_hooks.rs:174-177`）。
- この停止は attach と shutdown のたびに 5〜6 回走る。スレッドプールが激しく入れ替わる対象では、attach 時に Hook の群が黙って抜ける。shutdown で 2 回続けて失敗すると Hook が残り、そのプロセスには二度と attach できない。

### P2-9 Detour の中で、失敗するとプロセスを落とす確保と `lock().unwrap()` を使っている

- 軸: 堅牢性。確度: 仕組みは高。
- 対象がメモリ上限に近いとき（特に x86）、Detour 内の `Vec` や `String` の確保失敗は対象アプリを abort させる。記録なしならアプリが NULL を受けて処理できた場面（`engine/file_io.rs:287-299`、`engine/callbacks.rs:228-238`、`engine/com_methods.rs:208-226`）。
- Mutex を持ったまま panic すると poison され、以後の COM やファイル呼び出しがすべて Detour 内で panic する（`runtime.rs:1153`、`capture.rs:430-443`）。R41 が直したのは DLL の export だけ。

### P2-10 書き込み失敗（ディスク満杯）の扱い

- 軸: 堅牢性。確度: 高。
- Index と Finalization のための空きを確保していない。途中で満杯になると必ず Finalization のない Trace になる。
- Writer は失敗後の状態が壊れる。`write_block` は書く前に Index へ積み、`flush_blobs` と `flush_schemas` は書く前に待ち列を空にする（`writer.rs:645-651`、`writer.rs:564-600`）。現状は Host が再試行しないので実害は前項だけだが、再試行を入れると Blob 欠落や位置ずれになる。

### P2-11 壊れた入力や悪意ある入力で、上限を越えたメモリと CPU を使う

- 軸: 堅牢性。確度: 計算は高、実ファイルでは未試行。
- 展開後の構造体サイズを数えていない。数 KB の zstd Block が 256MiB に展開されると、`decode_loss_block` は 1.34 億件の `LossRecord`（約 10.7GB）を作ろうとする（`crates/shirusu-trace/src/proto.rs:612-622`）。Schema、Index も同じ形。
- 再同期は `SBLK` の候補ごとに最大 512MiB まで CRC を計算する。偽のヘッダーを詰めたファイルでは候補数×ファイルサイズになる（`reader.rs:588-642`）。N5 が直したのは確保量で、CPU は残っている。
- `parse_imports` は記述子 4,096 個と各 16,384 エントリの上限を持つが総数の上限がない（`crates/shirusu-hook/src/pe.rs:139,164`）。1MB 未満の細工したイメージで約 6,700 万件、6GB 以上になる。対象プロセス内と Host の両方から届く。

### P2-12 shirusu-test の JSON 文字列解析が二次時間

- 軸: 性能。確度: 高。
- 文字を 1 つ取り込むたびに、現在位置から文書の末尾までを `from_utf8` で検証し直す（`crates/shirusu-test/src/json_parse.rs:168-174`）。同じループを単体で測ると 1MiB の文字列で 17.3 秒。8MiB の上限では外挿で約 18 分。
- `shirusu-probe reduce` では子プロセスが既定 30 秒の制限を超え、試行がタイムアウトと誤判定される。

### P2-13 shirusu-compare が Blob を参照ごとに複製し、二次の経路を持つ

- 軸: 省メモリ、性能。確度: コードは高、未計測。
- Blob の内容を参照するイベントごとに複製する（`crates/shirusu-compare/src/normalize.rs:363-365`、`654-656`）。64KiB のバッファを 10 万回書く Trace は片側 6.4GB。
- 完了イベントごとにそれまでの全呼び出しを走査する（`normalize.rs:423-439`）。2,000 件を超える列の差分は貪欲法に落ち、不一致ごとに残りを線形探索する（`diff.rs:707-721`）。

### P2-14 1ms のつもりの待機が、タイマー分解能次第で最大約 15.6ms になる

- 軸: 性能、安定度。確度: 低〜中。Windows 実機未確認。
- 満杯時の上限付き待機は `WaitForSingleObject` に 1ms を渡す（`crates/shirusu-transport-win/src/lib.rs:1338-1343`）。Host の再確認も 2ms の同種の待機（`recorder_launch.rs:231-235`）。リポジトリのどこもタイマー分解能を上げていないので、通知が来ない場合の待ち時間は既定のタイマー周期まで伸び得る。
- 通知が正しく届いている間は表面化しない。Host が遅れたときに、アプリ側の停止が仕様の 1ms より長くなるかを実機で測る価値がある。

### P2-15 `repair` が ProfileSummary を引き継がない

- 軸: 堅牢性。確度: 高。
- `repair_trace` は `write_profile_summary` を呼ばない（`crates/shirusu-cli/src/repair.rs` に呼び出しがない）。`--mode profile` の Trace はその Block だけで成り立つので、修復後は中身が空になり「lost 0」と表示される。

## アーキテクチャ上の所見

個別の指摘の背後に、共通する構造が 4 つある。

1. 時間に比例して増える状態に上限がない。Writer の Index、欠落記録、`open_calls`、COM 追跡表、完了待ち I/O 表、呼び出し元キャッシュがどれもセッションの長さで増える。転送層の Ring と変換キューは厳密に上限管理されているのに、その外側が管理されていない。数時間の記録を前提にするなら、Index は分割して途中で書き出し、欠落記録は起きた時点で Trace に書く形が要る。
2. 書く側と読む側の上限が揃っていない。Writer は Block 数も総量も制限しないが、Reader は 100 万 Block、1GiB で止まり、解析ツールは全件をメモリに載せる。記録できた Trace を検証できない範囲が広い。ツールを `TraceStream` ベースの逐次処理に寄せるのが根本対応になる。
3. 高速経路は生成 API だけ。生成 Detour はロックも確保もない経路まで磨かれているが、手書きのファイル I/O、WndProc、COM、WinRT は `Arc` 複製、共有 Mutex、呼び出しごとの確保を持つ。実アプリで多いのは後者なので、HeapAlloc 中心のベンチマークで測った倍率は実アプリの倍率を代表しない。
4. Host の回収と変換がそれぞれ 1 スレッド。検証、変換、圧縮、書き込みが 1 本に直列で並び、Ring の引退やキュー満杯では回収側が変換を待つ。スレッド数が増えても Host の処理能力は増えないので、P1-1 を直して記録スレッドが増えると、次はここが詰まる。

着手順の提案は、P1-1（記録漏れが見えない）、P1-2 と P1-3（長い記録が完了も検証もできない）、V1〜V3（これらを検出できる計測）の順。P2-6 のフラグ取り違えと P2-5 の Mutex は数行で直る。

## 確認範囲と未確認事項

レビューはコードを読んで行い、ビルドと実行はしていない。例外は構造体サイズと JSON 解析ループの単体計測だけ。

- 直接通読した範囲: 転送層（shirusu-transport、shirusu-transport-win）、Agent、Agent DLL、Host、Trace の Writer とコンテナ、フックのランタイム（runtime、hazard、fls、caller、capture）、CLI の capture。
- 分担して通読し、結果の要点をコードで再確認した範囲: フックエンジン（engine、COM、WinRT、inline、bootstrap、pe、callback）、Trace の Reader と Stream、CLI の残り、analysis、compare、crc32c、probe、test、conformance、metadata-gen、emit、api-catalog、e2e、CI スクリプト、TLA+、fuzz、loom。
- 読んでいないもの: 生成物（`engine_generated.inc` 4.7 万行、`api_broad_generated.inc` 5.7 万行、`com_catalog_generated.inc`）は抽出確認のみ。各クレートのテストモジュールは概観のみ。ruzstd の内部は対象外。

Windows 実機で確認していない判断は次のとおり。

- P1-5: Ctrl-C が Host と対象にどう届くか、Host を失った Agent の挙動。
- P1-6: `CallWindowProc` ハンドルが返る条件と、呼んだときに落ちること。
- P2-4: Slot 再利用の競合が実際に起きる頻度。
- P2-8: スレッド入れ替わり中の停止失敗の頻度。
- P2-14: タイマー分解能による待ち時間の実測値。
- P1-2 と P2-1 の発生速度: Block 生成率と無圧縮化の割合はコードからの推定で、マルチスレッドの対象での実測が要る。

調べて問題なしと判断した点: Host の変換キューは 256MB で頭打ちになる。スレッド停止中の処理はヒープもロックも使わない。IAT の交換と復元、probe の子プロセス管理、fuzz の対象一覧は整合している。モジュールの署名確認は別スレッドで走り、回収を止めない。
