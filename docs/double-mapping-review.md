# A75 検討記録: Payload 終端またぎの二重マッピング最適化

状態: 検討済み（結論は **条件付き保留**。現行の分割コピーを正とし、採用条件が全て揃うまで再検討しない）

## 1. 対象と spec の原文

spec-transport.md（Payload 配置の節）:

> 終端をまたぐコピーを無くしたければ、同じ領域を仮想アドレス上で二重に並べて割り当てる方法がある（`VirtualAlloc2`と`MapViewOfFile3`、Windows 10 1803以降）。Windows 7対応と両立しないので、初版は分割コピーとし、後から最適化として検討する。

現行実装は分割コピー（`ring.rs` の `copy_payload_write` / `copy_payload_read`、項目 A11）で、終端をまたぐ場合は「末尾までの分」と「先頭からの分」の 2 回に分けてコピーする。C14（終端をまたぐ書き込み）で検証済み。

## 2. 方式の概要

二重マッピング（mirror mapping）は、同じ File Mapping を仮想アドレス空間上で隣接して 2 回マップし、リングバッファを「線形に続いているように」見せる手法である。

1. `VirtualAlloc2` で `MEM_RESERVE_PLACEHOLDER` を使って、Payload 領域の 2 倍のアドレス範囲を予約する。
2. 予約を 2 つに分割し、それぞれに `MapViewOfFile3` で同じ Mapping の同じオフセットを割り当てる。
3. 書き手/読み手は「位置 + 長さ」が終端を越えても 1 回の線形コピーで済む。2 つ目のビューが先頭の内容をそのまま映すためである。

対象になるのは Payload Ring のみ（Descriptor Ring は要素がリング末尾で綺麗に切れるため、またぎコピーが生じない）。

## 3. 前提条件と互換性

- `VirtualAlloc2` は Windows 10 version 1803 以降、`MapViewOfFile3` は Windows 10 以降の API で、Windows 7 / 8 / 8.1 には存在しない。spec 自身が「Windows 10 1803以降」と明記している。
- overview の開発環境表では Windows 7/8/8.1 は「互換性を検証して追加する」対象であり、現時点でサポート範囲から外す決定は無い。採用には「対象 OS の下限を引き上げる」という製品判断が先に必要であり、最適化の都合だけで決められない。
- 動的解決（`GetProcAddress` で存在確認し、無ければ分割コピーへフォールバック）は技術的には可能だが、その場合は両経路の実装とテストを恒常的に維持することになる（第 5 節）。

## 4. 期待される利得の見積もり

分割コピーの追加コストは、コピーする総バイト数には影響しない。違うのは次の 2 点だけである。

- `memcpy` の呼び出し回数が、またぎの場合に 1 回 → 2 回になる。追加分は呼び出しと境界計算のオーバーヘッドで、Payload 1 件あたり高々数十 ns のオーダー。
- 書き手/読み手のコードから境界分岐が消える（保守性の利得）。

またぎが発生するのは、書込位置が「容量 − Payload 長」より後ろにある場合だけで、大半の書込は元々 1 回のコピーで済む。A73 の調整値測定でも、記録経路のボトルネックはコピー回数ではなく待機と通知の経路だった。したがって、現行の利用実態ではスループットの利得は誤差範囲と見積もる。

## 5. コストとリスク

- **二重実装の維持**: 対応 OS の下限を変えない限り、分割コピー経路は残り、二重マッピング経路が追加分になる。両経路で「同じバイト列が同じ位置に書かれる」ことを保証するテスト（往復・折り返し境界の行列）も 2 系統必要になる。
- **障害モードの増加**: placeholder の分割/結合、片側ビューのマップ失敗時の縮退、プロセス終了時の解放順序など、Mapping のライフサイクル管理が増える。失敗時に「半分だけ映っている」状態を Host 検証がどう扱うかも決める必要がある。
- **Host 検証への影響**: 二重マッピングは Agent プロセス内での見え方の話であり、Mapping の実体は 1 つなので、Host 側の検証モデル（KnownConfig による範囲検証、コピーしてから検証する方式）は原理的には不変である。ただし Agent 側の位置計算がビュー前提に変わるため、検証側が前提とする「位置 = position % capacity」の解釈と食い違わないよう、共有メモリ上の Cursor と位置の意味は現行のままに保つ必要がある。
- **デバッグ性**: 同じ物理ページが 2 つの仮想アドレスに現れるため、メモリダンプや障害解析で混乱しやすい。

## 6. 結論

**条件付き保留とする。現行の分割コピーを正とし、二重マッピングは実装しない。**

理由の要約: 互換性の前提（Windows 7 対応）と両立せず、それを変える製品判断が無いこと。利得は測定上も見積もり上も小さいこと。得られるのは主にコードの単純さだが、フォールバックを含めると全体の複雑さはむしろ増えること。

次に挙げる条件が **全て** 揃った場合に限り、再検討する。

1. サポート対象から Windows 7 / 8 / 8.1 を外す決定が overview 側でなされている。
2. プロファイルの実測で、分割コピーのオーバーヘッドが記録経路の有意な割合（目安として 5% 超）を占めることが示されている。
3. フォールバック無しの単一経路にできる（条件 1 と対）、または二重経路の維持コストを受け入れる判断がある。

再検討の際は、本書の第 2 節の方式を起点に、Host 検証の前提（第 5 節）を変えない設計にすること。
