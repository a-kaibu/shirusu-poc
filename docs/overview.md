# shirusu 設計ドキュメント

Nov 8, 2026 · @こた

## 概要

shirusuは、WindowsアプリがWindowsに何を要求し、何を受け取ったかを型付きで記録するRust製のOSSである。記録はWindows上で行い、解析はWindows・Linux・macOSのCLIで行う。

想定する利用者は次の三者である。

- 互換レイヤーの開発者（Wine、ReactOS、エミュレータやブラウザー上の実装など）
- リバースエンジニアリングやアプリ解析を行う人
- 古いアプリやゲームを保存・移植する人

既存ツールとの違いは、全Win32 APIを型付きかつオブジェクト追跡付きで記録し、別の実装の記録と突き合わせられる点にある。apitraceはグラフィックスAPIに限られ、API Monitorは再生や比較を持たず、Process MonitorはOSイベントだけを扱う。

Windowsとの比較やテスト生成は主要な用途だが、本体には含めず独立したコンポーネントにする。互換実装を持たない解析用途でも、本体単独で価値が出るようにするためである。

## 観測レベル L0〜L4

APIごとに、どこまで深く記録できるかをL0〜L4で示す。これは「shirusuの能力」の指標であり、個々のTraceが完全かどうかは別の指標で示す（下記）。

| レベル | 名前 | 内容 |
| --- | --- | --- |
| L0 | 呼び出し対象として検出 | 動的解決を含め、実際に呼ばれ得るエントリとして把握している |
| L1 | 呼び出し記録 | 型が分かる引数・戻り値・呼び出し元を取得する |
| L2 | データ復元 | ポインタの参照先、文字列、構造体、入出力バッファを取得する |
| L3 | 状態追跡 | HANDLE、COM、メモリ、非同期処理、リソースの変更を関連づける |
| L4 | 再実行可能 | 必要な状態を復元し、別の実装でも操作を再実行できる |

インポートテーブル等から分かる静的な依存は、レベルとは別の「静的依存」情報として記録する。`GetProcAddress`で取得した関数のように、静的依存が無くても呼ばれるAPIがあるためである。

初期実装では、Win32 Metadataから幅広いAPIのL0〜L1を生成する。L2以上は、SALアノテーションと手書きの記録仕様（どのメモリをいつ読むか、何を生成・破棄するか）を使ってAPIごとに拡張する。COM、WinRT、動的に取得された関数、非公開APIには、Metadata以外の定義と検出の仕組みが必要になる。

### Traceの完全性

各Traceの完全性は、次の三つを別々に判定して記録する。

| 指標 | 対象 | 不完全になる例 |
| --- | --- | --- |
| Capture Coverage | 何を観測できたか | Hook失敗、未対応のABI、注入できないプロセス |
| Event Integrity | 観測したイベントが保存されたか | バッファ溢れ、破損、途中終了 |
| Semantic Completeness | 記録したイベントをどこまで解釈できるか | 出力メモリの仕様不足、未解決のObject ID、非同期完了の欠落 |

Event Integrityを失ったTraceは`incomplete`と判定し、CLIの終了ステータスでも失敗を知らせる。テスト生成は、三つの指標を見て使える範囲を決める。

## 記録境界とモジュール分類

モジュール分類（そのDLLが何者か）と記録ポリシー（どの呼び出しを記録するか）は分けて扱う。標準では、ApplicationとRuntimeからWindowsの公開APIへ入る呼び出しを記録する。例えば`fopen`経由の`CreateFileW`も記録される。

詳細調査モードでは、Windows内部の呼び出し（`CreateFileW`→`NtCreateFile`など）も記録できる。それぞれ実際に起きた別の呼び出しとして親子関係付きで保存し、再実行では同じ操作の下位呼び出しを重ねて実行しない。

API Setは契約名であり、実際のDLLと一致しない。そのため、論理的なAPI名と、実際に実行された実装モジュールの両方を記録する。

モジュールは名前ではなく、次の4分類で扱う。

| 分類 | 判定基準 | 標準の扱い |
| --- | --- | --- |
| Windows | System32・SysWOW64・WinSxSにあり、埋め込み署名またはカタログ署名でMicrosoft製と確認できる | アプリからの呼び出しを記録する |
| Runtime | VC++ Runtime、CLRなどの実行基盤 | RuntimeからWindows APIへの呼び出しは記録する。Runtime独自のAPIを記録するかは設定で選ぶ |
| Application | EXE、同梱DLL、サードパーティ製DLL | 観測対象 |
| Unknown | 出所を確定できない | Applicationとして観測し、分類が不確実であることを残す |

- 判定理由をTraceに残す。
- CLIからモジュール単位で分類を上書きできる。
- ロード先の解決では、KnownDLLs、API Set、SxSを考慮する。
- Windowsからアプリへ入るコールバック（WndProcなど）も別種のイベントとして記録する。

## 記録モードと性能目標

標準の`full`モードでは、高頻度APIも含めて対象境界の呼び出しを間引かずに記録する。`HeapAlloc`や`GetLastError`を暗黙に除外すると、後から復元できなくなるためである。

| モード | 高頻度APIの扱い | 用途 |
| --- | --- | --- |
| `full`（標準） | 対象境界の呼び出しをすべて保存 | 詳細解析、テスト |
| `profile` | 呼び出し回数・分布・所要時間を集計 | API依存関係と性能の調査 |
| `filtered` | 指定したAPI群だけ保存 | 問題箇所の集中調査 |

性能目標は、通常のGUIアプリを操作できることである。代表的なGUIワークロードで実行時間の増加を3倍以内、高負荷のケースで5倍以内を開発中の評価基準とする。保証値ではない。

- `full`はイベントを意図的に間引かないモードであり、どんな負荷でも記録を保証するモードではない。欠落したらTraceを`incomplete`として扱う。
- 実行時間の倍率は代表的なワークロードの目標とし、API一件あたりの追加遅延、記録スループット、バッファ使用率も別に測る。`GetLastError`のような短いAPIと数ミリ秒かかるI/Oでは、Hookの相対的な負荷が大きく異なるためである。
- 圧縮とディスクへの書き込みは、Agent外のHostプロセスで行う。
- Agent内部の処理が自分のHookを再び呼ぶ問題は、再入制御で防ぐ。これは利用者が指定するAPI除外とは別の仕組みである。

## Agent–Host転送

AgentはスレッドごとのSPSCリングバッファ（書き手一つ・読み手一つ）へイベントを書き、Hostが共有メモリから直接取り出す。通常の記録では全スレッド共通のロックを取らない。

- 共有メモリは、小さな固定長レコードのイベント領域、大きなバイナリ用のPayload領域、状態カウンタに分ける。
- 共有領域には生のポインタを置かず、オフセットと長さで表す。
- Agentは参照先メモリをコピーし終えてからイベントを確定（公開）し、Hostは確定済みのデータだけを読む。これが最初に確立する転送の契約である。
- PayloadはAgent–Host間で独立したIDを持たない。Hostは検証済みのRing識別情報、Generation、Sequence、Payloadの論理オフセットから内部管理用の一時キーを生成する。HostがPayloadのBLAKE3を計算してBlobを保存した後、公開TraceではBlob IDを参照する。一時キーは公開形式に含めない。
- Hostの取り出しは、Agentのスレッドや対象プロセスのロックに一切依存しない。通知には待たない操作（イベントのセットなど）だけを使う。
- スレッドの生成・終了に伴うリングの登録と回収は、通常の記録経路とは別に管理する。

バッファが満杯のときの扱いは次のとおりとする。無期限に待つことはしない。

| 状況 | 動作 |
| --- | --- |
| 空きがある | イベントを記録する |
| 空きが少ない | Hostへ取り出しを要求する |
| 満杯 | 上限付きで短時間だけ待つ。上限は設定可能で、`0`なら待たない |
| 上限を超えても満杯 | イベントを捨て、欠落数と区間を状態カウンタに記録する |
| Hostが停止 | 対象アプリはそのまま実行を続け、記録の失敗を報告する |

Hostが対象プロセスに依存せずに取り出せるので、上限付きの待機はデッドロックを起こさない。Loader Lockを保持している可能性がある経路（DLL初期化中など）では待たない。

## Hookの透明性

Hookは、元の呼び出しでアプリから観測できる実行状態を変えてはならない。記録の正確さとは別の独立した要件として扱う。

- `LastError`：元のAPIから戻った直後にTEBから直接読み取り、Wrapperから戻る直前に同じ値を書き戻す。記録処理中にWindows APIを呼んでも結果が変わらないようにする。
- ABI：呼び出し規約、浮動小数点レジスタ、必要なCPUフラグ、スタックの整合性を保つ。x64の浮動小数点引数、可変長引数、構造体の戻り値には個別の規則があるため、Metadataから型が生成できてもそれだけでは正しいWrapperにならない。
- 例外：元のAPIが投げた例外はそのまま伝え、中断した呼び出しを`CallAborted`として記録する。
- 再入：コールバック中のAPI呼び出しは入れ子の呼び出しとして記録する。Agent自身の呼び出しは記録しない。

全Hook共通のABI適合性テストを用意する。浮動小数点引数、構造体の戻り値、コールバック、例外、`LastError`を扱うProbeを、Hookありとなしで実行して結果を比べる。

## プロセスの起動・アタッチとAgentの初期化

起動とアタッチの両方に対応し、子プロセスも追跡する。対象はそのプロセスツリーに限り、無関係なシステムプロセスは自動でフックしない。保護されたプロセスなど、Agentを注入できないプロセスもある。その場合はCapture Coverageに記録する。

- `shirusu capture -- app.exe`：`CREATE_SUSPENDED`で起動し、アプリのコードが動き始める前にAgentを準備する。CREATE\_SUSPENDEDが保証するのはメインスレッドが動かないことだけなので、Agentの初期化が完了したことはHostが別に確認する。
- `shirusu attach <PID>`：動作中のプロセスにAgentを入れる。アタッチ前の呼び出しや、その時点で既に存在するオブジェクトの来歴は不明としてTraceに記録する。
- 子プロセス：ランチャーから本体を起動するアプリを想定し、自動でAgentを入れる。子プロセスの発見とAgentの注入は別の実装として扱う。

Agentの初期化では、`DllMain`内で大量のHookを設定しない。Loader Lockを保持したまま複雑な処理を行うと、デッドロックの原因になるためである。ロードとHookの初期化を段階に分け、初期化が完了したことをHostが確認してからメインスレッドを再開する。

Hookは次の順に実装する。

1. IAT Hook：通常のDLLインポートを捕捉する。記録パイプラインの検証に使う。
2. Inline Hook：`GetProcAddress`経由や間接呼び出しを捕捉する。命令の再配置には`iced-x86`を使う。
3. COMのvtableインターセプション：次節で述べる。

## COM

COMは最初の段階（L1）から対応する。DirectX、DirectDraw、ShellなどはほぼCOMであり、後回しにすると「全APIを浅く記録する」という目標に大きな穴が開く。

- 既知のFactory関数（`CoCreateInstance`、`Direct3DCreate9`など）が返したインターフェイスを起点に追跡し、そのvtableのメソッド呼び出しを記録する。
- メソッドが返すインターフェイスや`QueryInterface`の結果も、追跡対象に加えていく。
- 同一性は、対象アプリが実際に実行した`QueryInterface`の結果だけで判定する。shirusuは標準では`QueryInterface`を追加で呼ばない。参照カウントを増やし、アプリがしなかったCOM操作になるためである。
- 同一性を確定できないインターフェイスは別々に保持し、関係を未確認とする。追加の`QueryInterface`による識別は、実行に影響し得る診断用オプションとする。
- `AddRef`と`Release`で寿命を追う。途中から発見したポインタや型が不明なカスタムインターフェイスは、未対応として明記する。
- Interception方式ごとに副作用が異なる。共有vtableの書き換えは同じ実装を共有する別オブジェクトにも及び、Proxyはアプリへ返すポインタの同一性を壊し得る。COM Adapterごとに、方式・対象範囲・同一性を保てたかを検証するテストを用意する。

## Trace形式

Traceは、独自のBlock Containerに、Protobufで書いたメタデータと、Schemaに従うCompact Binaryで書いたAPI引数を載せた形式にする。各チャンクは独立したZstdフレームで圧縮する。ストリーミングで書き込み、途中で切れても残りを読めるようにする。

用語は次のように使い分ける。Blockはファイル内の物理的な記録単位、Event Batchは複数イベントの論理的な集合、Event ChunkはEvent Batchを格納するBlockの一種である。

### 四つの層

| 層 | 担当 |
| --- | --- |
| Trace Container | Block、圧縮、チェックサム、索引、ストリーミング |
| Event Encoding | API呼び出し、プロセス、スレッド、時刻、同期、例外 |
| Typed Values & Resources | 構造体、ポインタ、HANDLE、COM、メモリ、Blob |
| API Schema | Win32、COM、WinRT、Legacy API、独自拡張 |

層を分けることで、API定義が増えてもContainerは変わらず、圧縮方式を変えてもイベントの意味は変わらない。ContainerとSchemaは別々にバージョンを持つ。

### 転送形式とディスク形式

AgentからHostへの転送形式は非公開で、いつでも変えてよい。ディスク形式は公開仕様とし、互換性を維持する。

Agentは引数と参照先のメモリを固定レイアウトのレコードとしてスレッド別の共有バッファに書き、Hostが公開形式へ変換して圧縮する。Hostが遅いとバッファが埋まり、最終的にはアプリを待たせる。そのため、ベンチマークではAgentの観測コスト、Hostの処理量、ファイルサイズ、デコード速度を別々に測る。

### ファイル構造

1. File Header：Magic、形式バージョン、Session ID、Feature Flags
2. Capture Environment：Windowsのバージョンとビルド、CPUとABI、記録設定、時計情報
3. Schema：初期の関数・COMインターフェイス・型の定義
4. Event Chunk（繰り返し）：Schemaの部分集合、ローカル辞書、時刻の基準値、イベント列
5. Blob Chunk（繰り返し）：メモリ、画像、音声などのバイナリ
6. Schema Checkpoint（途中に定期的に）：その時点までに必要になった定義の複製
7. Index（省略可）：API・プロセス・時刻・オブジェクト別のオフセット
8. Finalization（省略可）：正常終了の印。無ければ途中で終わった可能性がある

DLLのロードやCOMインターフェイスの発見で定義が増えたら、記録の途中でSchemaを追加する。各Blockは種類、圧縮方式、シーケンス番号、圧縮前後のサイズ、チェックサムを持ち、未知のBlockは読み飛ばせる。

### イベントの符号化

頻度の低いデータはProtobuf、APIの引数と戻り値はSchemaに従うCompact Binaryで符号化する。

- Protobuf：Environment、Schema、モジュール、オブジェクトイベント、索引。フィールドの追加と他言語への公開が容易になる。
- Compact Binary：`CallEnter`と`CallLeave`の引数・戻り値・出力値。Schemaが型と順序を定めるので、値ごとの型タグは持たない。取得状態とBlob参照だけを付ける。
- 共通情報：Session、Process、Thread、Writer、時計はバッチのヘッダーに一度だけ書き、各イベントは時刻の差分とシーケンス番号だけを持つ。

Compact Binary仕様には、整数の幅とバイト順、ポインタの表現、文字列の符号化、NULLと取得失敗の区別を定める。一度発行したSchema IDが表すバイナリレイアウトは変更しない。意味情報を足すときは、互換性のあるAnnotationを追加するか、新しいSchema IDを発行する。

Schema IDはファイル内の連番とする。別のTraceどうしで同じ定義かを判定できるよう、各定義には正規化した内容のハッシュも付ける。

### 型付きの値

生の値とデコードした値の両方を保持する。例えば`CreateFileW`のパスは、ポインタのアドレスと、その先のUTF-16文字列の両方を持つ。解析方法を後から改善しても、元の値で検証し直せるようにするためである。

- 取得状態：`Captured`、`Unreadable`、`Truncated`、`Unsupported`を区別する。読めなかった値をNULLとして保存しない。
- 浮動小数点数：生のビット列で保持し、NaNのペイロードも失わない。
- アドレス：アドレス空間、ポインタ幅、必要ならセグメントを付ける。Win16のFar Pointerも同じ仕組みで表す。
- `GetLastError`：生の値と、API仕様上意味のあるエラー値を区別する。

メモリの取得タイミングはSchemaで引数ごとに定める。入力バッファは呼び出し前（`before`）、出力バッファは元のAPIが書き込んだ後（`after`）、非同期I/Oは完了時（`completion`）に取得する。入出力が同じバッファなら前後の両方を保存できるようにする。

### ID体系

| ID | 意味 |
| --- | --- |
| Session ID | どの記録に属するか |
| Process ID | Trace内で一意なプロセスの識別子。PIDの生値は別に記録する |
| Thread / Writer ID | イベントの書き手。順序番号はこの単位で単調増加する |
| Call ID | `CallEnter`と`CallLeave`の対応、親子関係 |
| Object ID | HANDLE、COM、GDIなどのリソース。HANDLEの生値は別に記録する |
| Blob ID | バイナリの内容（BLAKE3、256bit） |

Blob IDが同じでも、データが同じだけで、Windowsのオブジェクトが同じとは限らない。

### 順序と時計

標準では、Writerごとの単調増加番号、`QueryPerformanceCounter`の値と周波数、Call IDと親子関係、同期イベント（Mutex、Event、Wait、非同期I/Oの完了）を記録する。

`--order=global`を付けると、フックの観測点ごとに全スレッド共通の番号を振る。この番号はアトミックカウンタを更新した順序であり、API処理の完了順やメモリ操作全体の順序を保証しない。別のPCで取ったTraceどうしは時刻の原点が異なるので、時刻だけで対応づけない。

### チャンク、圧縮、Blob

- 各Event Chunkは、自分をデコードするのに必要なSchemaの部分集合とローカル辞書を持つ。部分集合には、参照する構造体や型の依存先まで含める。これで「独立デコード可能」（チャンク単独で型とイベントを解釈できる）になる。参照先のBlobやオブジェクト状態まで含めて復元できる「リソース復元可能」とは区別する。Blobが壊れても、API呼び出し自体は検索できる。
- 圧縮はチャンクごとの独立したZstdフレームで行う。チャンクの大きさは非圧縮で256KiB〜1MiBを目安に、ベンチマークで決める。
- Zstdの学習済み辞書は初版では使わない。測定して効果があれば追加し、参照するチャンクより前に保存する。
- BlobはBLAKE3で内容を識別し、同じ内容は一度だけ保存する。初版では前方参照を許さず、Blobを参照するEvent Chunkより先に書き込む。部分的な更新は、Resource ID、オフセット、サイズ、更新内容で表す。元データは可逆圧縮だけで保存する。

### 完全性と復旧

- チャンクの破損はCRC32Cで検出する。対象はBlockのヘッダーとペイロードで、チェックサム欄自身は除く。改ざんの検出は目的にしない。
- 「チャンクの破損」「イベントの欠落」「意味情報の不足」「参照先Blobの喪失」を区別して報告する。
- 対象アプリがクラッシュしたら、Hostが共有バッファに残ったイベントを回収する。HostやOSがクラッシュしたら、最後に永続化されたチャンクまで復旧する（`flush`と`fsync`の設定で保証範囲が決まる）。
- `shirusu repair`は正常なチャンクと参照関係を検証して、読めるイベントを回収する。失われたイベントを推測で作らない。

### 安全性と検証

Traceは外部から来る信頼できない入力として扱う。Readerはサイズ、参照数、展開後サイズに上限を設け、循環する参照を拒否する。初期マイルストーンから`cargo-fuzz`で、異常な長さフィールド、壊れたProtobuf、未知のSchema、壊れたZstd、欠けたBlob、途中で切れたチャンクを検査する。仕様には言語に依存しないテストベクターを付ける。

Traceにはファイルパス、個人情報、認証情報、アプリのアセットが含まれ得る。Readerは初版ではRustの参照実装だけを提供し、他言語からはJSONLとParquetで利用してもらう。CPU命令イベントの符号化は今は決めず、将来のBlockの種類として追加する。

## 対応OSとアーキテクチャ

最初に正式対応するのはWindows 10/11のx86とx64である。

| OS | Capture Agent |
| --- | --- |
| Windows 10 x86 | i686 Agent |
| Windows 10/11 x64 | x86\_64 Agent＋WoW64上の32bitアプリ向けi686 Agent |
| Windows 11 ARM64 | 将来のARM64 Agent＋エミュレーションで動くx86・x64アプリ向けAgent |
| Windows 7/8/8.1 | 互換性を検証して追加する。Rustの`*-win7-windows-msvc`（Tier 3、stdあり）を自前でビルドする |
| Windows XP以前 | 専用の軽量Agentを検討する |
| Windows 9x/3.x | 別のABI・別のCapture Backendとして扱う |

記録は対象プロセスと同じアーキテクチャのAgentで行う。32bitアプリにはi686のAgentを、x64アプリにはx86\_64のAgentを入れる。

## CLIとコンポーネント構成

記録はWindows上のHostとAgentが行い、できたTraceはWindowsに依存しないReaderでどのOSからでも読める。他の互換実装も同じ形式でTraceを出せば、同じツールで解析・比較できる。

| コマンド | 動くOS | 内容 |
| --- | --- | --- |
| `shirusu capture -- <exe>` | Windows | 起動して最初から記録する |
| `shirusu attach <PID>` | Windows | 動作中のプロセスを途中から記録する |
| `shirusu inspect <trace>` | 任意 | モジュール、完全性、API別の集計を表示する |
| `shirusu export <trace> --format jsonl` | 任意 | jqで調べられるJSONLに書き出す |
| `shirusu export <trace> --format parquet` | 任意 | DuckDBなどでSQL検索できるParquetに書き出す（後日） |

API、プロセス、スレッドなどの基本的な絞り込みはCLIのオプションで提供し、独自のクエリ言語は作らない。

## 比較とテスト生成

比較（`shirusu-compare`）とテスト生成（`shirusu-test`）は、本体とは別のコンポーネントとして提供する。記録と解析だけを使う人は、本体だけで済む。

比較では、呼び出し列を単純に並べて照合しない。正しい互換実装でも、内部処理が違えば呼び出しの回数や順序は変わるためである。代わりに、オブジェクトの種類、生成した操作、後続の参照関係から両側のオブジェクトを対応づけ、API契約と状態変化を比べる。

テストは、言語に依存しないJSON仕様を正規形式にする。画像やメモリなど大きなバイナリは別ファイルに置き、JSON Schemaも公開する。

- 出力先：Windowsのx86・x64向けProbe exeを生成できる。exeを動かせない互換実装には、JSON仕様をそのまま解釈するRunnerを用意する。
- 期待値：Windowsで毎回取り直す方式と、保存済みGoldenを使う方式の両方に対応する。GoldenにはWindowsのバージョン、CPU、ロケール、GPUの情報を付ける。
- 前提条件の検査：Traceからテストを作るとき、初期状態やコールバックなど再実行に必要なものが足りなければ、その不足を報告する。

## 検証計画

トレーサーが誤った値を記録すると、後の解析がすべて誤った前提に立つ。イベントが取れたことだけでは合格にせず、次の三つを独立して検証する。

| テスト | 検証すること |
| --- | --- |
| Correctness | 引数、戻り値、出力メモリ、呼び出し元、イベントの親子関係が期待どおり記録されるか |
| Transparency | shirusuなしとありで、アプリの機能的な結果が変わらないか。スレッド間のタイミングなど、同一性を保証できない部分は区別する |
| Performance | Hookのみ、L1記録、L2のメモリ取得、Hostの圧縮・保存の各段階で、処理時間とイベント生成量を測る |

Readerに対する`cargo-fuzz`は、最初のReader実装から継続して動かす。

手法ごとの役割、TLA+の不変条件、CIでの実行方針：検証戦略

## 初期マイルストーン

最初の技術的な成立条件は、Agentが任意のWindowsスレッド内で動いてもアプリを壊さず、観測したイベントをHostへ安全に渡せることである。APIの種類を増やす前に、この土台を固める。

| 段階 | 実装・検証するもの | 合格条件 |
| --- | --- | --- |
| 0 | Event Model、転送の契約、公開Trace仕様の最小版 | x86・x64と複数スレッドのイベントを表せる |
| 1 | Agent→Hostの共有メモリ通信 | 欠落・Host停止・スレッド終了を検出できる |
| 2 | Trace Writer/Readerと復旧 | クラッシュで途中で切れたTraceを解析できる |
| 3 | IAT Hookと手書きWrapper | 引数・戻り値を正しく記録し、対象の結果を変えない |
| 4 | Win32 Metadata Generator | L1の対象APIを増やせる |
| 5 | Inline Hook、呼び出し元の分類 | 動的解決や間接呼び出しを検証できる |
| 6 | COM Interception | 同一性・参照カウント・寿命を壊さない |
| 7 | 起動・アタッチ・子プロセス | 開始時点と捕捉範囲を正しく管理できる |
| 8 | JSONLの書き出し、索引、repair | Windows以外のOSでも記録を調べられる |

検証には、まず自作の小さなプログラムを使う。ファイル・レジストリ・スレッドを使うコンソールアプリ、USER32・GDI・DIBを使うGUIアプリ、COMを使うアプリである。その後、実アプリでどこまで記録できるかを評価する。
