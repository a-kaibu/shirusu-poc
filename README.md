# shirusu-poc

shirusu の Agent–Host 転送仕様 v0.4（SPSC Ring と状態遷移）の PoC 実装。
仕様の正は `docs/spec-transport.md`、全体設計は `docs/overview.md`、検証戦略は `docs/verification.md`。
仕様条項・テスト項目と実装の対応は `docs/traceability.md`（網羅チェックリスト、進捗の分母）にあります。

> 範囲について: 最初の実装対象は `shirusu-transport` の SPSC Ring と状態遷移です。
> Hook、公開 Trace への変換、COM はまだ実装しません（spec.md 末尾の決定）。
> Host への再接続も初版では扱いません。予備 Queue は実装しません（理由は所感 2026-11-09 00:41）。

## 構成

| クレート | 内容 | Windows 依存 |
|---|---|---|
| `crates/shirusu-transport` | 共有メモリレイアウト、SPSC Ring、Payload、Overflow 状態機械、Slot、通知ロジック、Host 検証、CRC32C | なし |
| `crates/shirusu-transport-win` | File Mapping（名前なし）、DuplicateHandle、Event Object（data_ready: プロセス単位 auto-reset / space_available: Ring 単位）、2ms 再確認付き待機、継承ハンドル付き子プロセス起動 | あり（他 OS はスタブ） |
| `crates/shirusu-agent` | 書き手側。スレッド毎 Ring 取得・書込、再入ガード、Host 生存確認、DETACH 通知 | transport-win 経由 |
| `crates/shirusu-host` | 読み手側。Drain Worker、検証付き読み、Loss Event 生成、Enter/Leave 対応付け、終了不明判定、完全性報告 | transport-win 経由 |
| `crates/shirusu-loom-tests` | loom による公開/回収プロトコルの網羅検査モデル | なし |
| `e2e/` | Test Supervisor / producer / consumer。同期ポイント経由のシナリオ群と、Windows でのプロセス間実テスト | 一部 |
| `fuzz/` | cargo-fuzz ターゲット 3 件（validate_control / decode_descriptor / decode_payload）とシードコーパス | なし |
| `tla/` | TLA+ モデル（SPSC Ring + Slot 再利用 + スレッド終了、容量 2・書手 2・読手 1）と TLC 設定 | なし |

転送の核となる契約は 1 つです。

- 書き手: Payload コピー → Descriptor 書込 → `write_cursor` を Release 更新（公開点はここだけ）
- 読み手: `write_cursor` を Acquire → 確定分だけコピー → 検証 → `read_cursor` / `payload_read_position` を Release 更新

通常経路ではプロセス共通ロックも全順序フェンスも使いません。満杯時は既定 1ms まで待って
OVERFLOW に入り、まず Payload だけ落として Descriptor を残し、それも無理ならイベントを捨てて
Loss カウンタと Sequence 欠番で欠落を残します。

## 使い方

```bash
# ビルドとテスト (Linux/macOS でも transport の核は動く)
cargo test --workspace
cargo test -p shirusu-loom-tests

# Windows ターゲットのコンパイル確認 (Linux から)
cargo check -p shirusu-transport-win -p shirusu-agent -p shirusu-host --target x86_64-pc-windows-msvc
cargo check -p shirusu-transport-win -p shirusu-agent -p shirusu-host --target i686-pc-windows-msvc

# E2E シナリオ (プロセス内 + 子プロセス起動スモーク)
cargo build --workspace
./target/debug/shirusu-e2e-supervisor --all
# Windows: x86 producer + x64 host のプロセス間実テスト
#   $env:SHIRUSU_E2E_PRODUCER = "target\i686-pc-windows-msvc\debug\shirusu-e2e-producer.exe"
#   .\target\x86_64-pc-windows-msvc\debug\shirusu-e2e-supervisor.exe --cross-arch
```

CI と同じ手順は `scripts/ci/` にあります（`linux.sh` / `windows.ps1` / `windows-x86.ps1` /
`kani.sh` / `fuzz-short.sh` / `tla.sh`）。GitHub Actions の定義は `.github/workflows/` です。

## 実装して感じたこと

作業の節目ごとに追記しています（後付けの作文ではなく、その時点で気づいたこと）。

### 2026-11-09 00:31 — Descriptor を 64B に詰める理由は「検証の単位」だった

仕様の表だけ見ると 64B はキャッシュラインへの配慮に見えるが、実装してみると意味が違った。
Descriptor がちょうど 1 キャッシュライン = 固定 64B だと、Host 検証は「64B をコピーしてから
検証する」が機械的に書ける。サイズが可変だったら、検証前のコピー自体が入力依存になって
しまう。レイアウトの静的アサーション（offset_of まで全部止める）は、x86/x64 混在のためと
いうより、将来フィールドを足したくなったときに必ず誰かが気づくための柵だと感じた。

### 2026-11-09 00:38 — 通知の取りこぼしは「正しさ」ではなくコスト配分の問題

v0.1 方式が Release/Acquire で動かない理由をコードに落とすと、結局「全順序フェンスを
毎イベント打つか、2ms の再確認で諦めるか」の配分でしかない。フェンスを通常経路に入れない
設計は、コードでは「notify モジュールが順序付けを一切触らない」という形にすると一番
素直だった。閾値越え通知も、ラッチを持たせないと「越えている間ずっと SetEvent する」
素朴な実装になりがちで、テストで初めて気づいた。

### 2026-11-09 00:41 — Payload 先落としは割り切りだが、L1 の線引きが救いになる

Overflow で Payload だけ落とす判断は、実装すると「Descriptor は残るのに中身が無い」
という中途半端な状態をたくさん作る。救いなのは、落とした理由を値ごとに残し、
「Payload を落とした呼出は L1 として扱わない」を型（CaptureState）で表せること。
この線引きが無いと、下流が骨格だけのイベントを完全な記録と誤認する。逆に言うと、
この割り切りは Host 側の完全性報告まで実装して初めて成立する。片方だけでは嘘になる。
なお予備 Queue を捨てた判断（v0.4）にも同意する。実装を考えると、Queue は「もう 1 本
Ring を作る」のと同じだけの検証対象を増やすのに、得られるのは Slot 不足の緩和だけだった。

### 2026-11-09 00:47 — Host が共有メモリを信用しない代償は「二重の簿記」

検証モジュールを作ると、Host は Cursor・世代・カウンタの全部について「前回値」を
自分側に持つ必要が出てくる。共有メモリの値を読むだけの素朴な Host の倍の状態量になる。
それでも、検証の順序（世代 → Cursor 後退 → カウンタ）を間違えると、別 Ring の像を
「Cursor が後退した破損」と誤判定することをテストで踏んだ。誤判定は「止めるべきでない
Ring を止める」方向のバグで、検出漏れより実害が大きい場面があると思う。

### 2026-11-09 00:55 — ストレステストの設計ミスは、製品のバグより先にテストが嘘をつく

SPSC 並行テストで、劣化イベントを正常件数に数えたため reader が早期終了し、
producer が空転してテストがハングした。製品側の契約（劣化は公開だが正常ではない）を
テストが正確に写せていなかった。100k 件の数字だけ大きくしても、数え方を間違えると
検証にならない。「何を 1 件と数えるか」は転送の意味論そのものだと実感した。

### 2026-11-09 01:02 — loom と実プロセスの差は、loom が正しいほど気になる

loom のモデルは公開/回収の順序を網羅してくれるが、モデルの Ring は自分で書いた
最小版なので、「実装の写し絵を検査している」危険が常にある。参照モデルと実装を
独立させるという test.md の注意は PBT だけでなく loom にも効く。実プロセス間
（File Mapping、Handle 寿命、プロセス終了）は loom では一切見えないので、
Windows E2E を CI で実走させることに意味がある。逆に、CI でしか見えない失敗を
ローカルの loom/PBT に還元できる形（同期ポイント、仮想時計）で E2E を書くべきだった。

### 2026-11-09 01:16 — TLA+ の状態爆発は「無制限な Generation」が起こしていた

TLC が終わらなかった原因は Ring ではなく Slot の Generation だった。Claim/Reclaim の
サイクルは Cursor を進めずに Generation だけ増やせるので、状態空間が無限に伸びる。
制約に Generation <= 2 を入れたら 12 秒で終わった。「再利用を 1 回だけ許す」モデルでも
不変条件の検査としては十分で、境界をどこに引くかはモデルの設計そのものだと分かった。
Kani のセットアップが tar の所有権で落ちた件も含め、検証ツールは「導入できるか」が
最初の関門で、CI 側のスクリプトに回避策 (TAR_OPTIONS) を残す価値があった。

### 2026-11-09 01:39 — チェックリスト自体に漏れがある。仕様の再読が分母を増やす

実装が一通り終わった後に spec を条項ごとに読み直したら、チェックリストに無い
仕様が 5 つ出てきた。空き待ち経路の全順序フェンス（A61）、共有メモリセクションの
アクセス制御（A62）、Slot Pool の総メモリ上限（A63）、Host 突然終了時の
Finalization 不在の扱い（A64）、待機方式のベンチマーク選定（A65）。A61〜A64 は
この場で実装し、ローカルテストまで通した。A65 はベンチマークハーネスが無いので
未着手のまま残す。分母は 135→140 に増えた。
教訓は二つ。ひとつは「全部実装した」という感覚はチェックリストの完全性に依存
していて、チェックリスト自体が間違うこと。もうひとつは、仕様の文は「〜する」
と「〜できるようにする」を混ぜて書くので、後者（上限の設定可能性など）は
実装の有無を判定しにくく、見落としやすいこと。フェンスの件は、待機が
ポーリング実装だと動いてしまうためテストが無ければ気づかない類の抜けで、
フラグを消すミューテーションでスレッドテストが落ちることを確認してから
採用した。ACL は Windows でしか動かず、ローカルでは cargo check までしか
確認できない。こういう項目は CI が通るまで「実装済み未検証」のまま置くのが正しい。

大きな Snapshot の Fragment 取得中に元メモリが変わり得る問題は、文書に一行書くだけなら
読み手が忘れる。`SnapshotOutcome.simultaneity_guaranteed: false` のように結果の型に
必ず現れる形にすると、使う側が握りつぶしにくい。保証しないものを「しない」と
表明するフィールドは無駄に見えて、表明し忘れを防ぐ柵になる。

### 2026-11-09 01:45 — 配布経路の都合が、テスト資産の保持形式を決めた

fuzz の種はバイナリであることが本質だが、このリポジトリへの push 経路
（GitHub API のスナップショット）が UTF-8 テキストしか運べず、バイナリ種を
含む push は全体が拒否された。そこで正の種を hex テキストで保持し、
`corpus/` は生成物に格下げした。検証資産の形式は「検査に最適か」だけでなく
「配布・保存の経路を通るか」でも決まる。往復のハッシュ一致を確認してあるので
情報は落としていないが、経路の制約が設計に漏れ込む好例になった。

### 2026-11-09 02:52 — 通知の結線は「部品がある」だけでは終わらない

A61 の空き待ちフェンスと通知は、ライブラリ単位では `drain_*_with_space_notify`
にクロージャを渡す形で揃っていた。しかし Host プロセスが毎回同じ結線を書く
設計だと、書き忘れがそのまま通知欠落になる。結線を `NotifyingDrainWorker`
に集約して、回収と `space_available` の SetEvent を 1 か所で結んだ。
E2E シナリオでは書き手を 3 回待機に入れて、通知がちょうど 3 回飛び、欠落なく
16 件が再開することを確認した。通知回数が待機エピソードと一致するのは、
「回収した分だけ・待っているときだけ」通知できている証拠で、回数そのものが
仕様の確認になっている。`space_notifications` のようなカウンタは、デバッグ用
というより「通知が仕様通りの回数だけ飛んだか」を数えるためのものだと気づいた。

### 2026-11-09 02:52 — 待機方式は Event に決まったが、収穫はスタブの嘘に気づいたこと

ベンチ（50 ラウンド）では Event が中央値 14µs / p95 24µs で、sleep 方式の
中央値 48µs / p95 97µs を上回った。sleep の p95 に 1ms 超の外れがあったのは、
スリープの粒度がスケジューラに左右される尾のリスクで、イベント方式が尾も
抑える。数字より収穫だったのは、Linux スタブの EventObject が 1ms ポーリング
だったことに気づいたことだ。スタブのまま EventClock を作っても、Linux では
sleep 方式より遅くなり、ベンチの数字が嘘になる。condvar ベースの真の
ブロッキング待機に書き換えたら、イベント方式の待機ループ回数は sleep の
約 1/10 になった。スタブは「API 形だけ保つ」つもりでも、タイミングの意味論
まで似せないと計測が成立しない。残りは Agent が Host から space_available
ハンドルを受け取る受け渡し（A68）で、ここはプロセス間の設計が要る。

### 2026-11-09 03:29 — 受け渡しは「ハンドルを渡す」だけでは終わらない。使う側の Clock まで差し替える

A68 で Host→Agent の `space_available` 受け渡しを実装した。`EventObject` に
`DuplicateHandle` 経路が無かったので、まずそこから作った。`SharedMapping` の
複製と並べると、Event の複製は Handle の寿命の扱いだけが違う（複製した
ハンドルから作った `EventObject` を Drop すれば複製側が閉じる）。Agent 側は
ハンドル値から `RingNotify` を作り、`EventClock` を Clock として差し替える
`attach_space_available` を用意した。ここで気づいたのは、Agent の Clock が
`thread_begin` の時点で書き手に複製されるため、受け取りが遅れると既存の
書き手が古い Clock を掴んだままになることだ。差し替えは書き始め前に限る
（遅れたら `None` を返す）という制約を、便利さより正しさで選んだ。
受け渡しの実証は 2 段にした。Windows 実機では自プロセスへの複製で SetEvent
が複製側から観測できるテスト（GHA で回る）。Linux ではプロセス内共有の
同じ `Arc<RingNotify>` で Agent と Host を結び、E2E で書き手が EventClock
で待機したこと（`sleep_calls() > 0`）を確認する。ミューテーション確認では
Clock の差し替えを外すと E2E が `event_waits=0` で落ち、他の観測は全て
通った。シナリオが「ハンドルが渡ったか」ではなく「渡った先で待機に使われたか」
を見ている証拠になる。残る未着手は D41 の CI フィードバックループのみで、
それは一括 push と kota の判断を待つ。

### 2026-11-09 — 「テストが足らない」は測定したら本当だった

「全然テストが足らない」という指摘を受けてカバレッジを測ったら、全体で
71% しかなく、最悪の crc32c は 67% だった。面白いのは未達行の顔ぶれで、
`make_table` の本体——CRC テーブルを生成する const fn そのもの——が丸ごと
未実行だった。実行時にテーブルを参照するテストは幾らでもあるのに、生成は
コンパイル時に終わっているから、誰も「実行した」ことにならない。対策は
const 版と実行時版 (ビット演算リファレンス) の差分照合で、カバレッジと
正しさの両方を一度に取れた。ミューテーションも同じ構図で、88 件のテストが
554 件の mutant のうち 75 件を取りこぼし、その多くは「値を返すだけの
アクセサ (容量・空き数・次シーケンス覗き見) を誰も直接 assert していない」
という地味な穴だった。テストの「件数」は安心感をくれるが、効いているかは
別の物差しが要る、という当たり前を数字で殴られた回。

### 2026-11-09 — 損失の「見え方」は観測点で違う

損失会計の保存則プロパティを書くとき、公開数 = 受信数 + 損失数の等式が
末尾のドロップで崩れて何度か悩んだ。理由は単純で、シーケンス欠番として
観測できる損失は「その後に受信できたイベント」があって初めて姿を現す。
末尾で落ちたイベントは欠番にはならず、カウンタの中にだけいる。つまり
「欠番の合計」と「ドロップカウンタ」は別の観測量で、突き合わせるなら
総和側で閉じる式にしないといけない。100 万イベントのソークではこの形で
完全一致した (受信 64,201 + 損失 935,799 = 1,000,000)。会計の式は
仕様の文面より先に「何で観測するか」を決めないと書けない。

### 2026-11-09 — Dekker のつもりが Store Buffer だった

通知の lost-wakeup を loom でモデル化したら、厳密な Dekker 式の主張
(「両者が互いを見逃すことはない」) が普通に反例を出した。実装の順序付けは
Release ストア + Acquire ロード + 片側だけの SeqCst フェンスで、この組合せ
では両者見逃し (Store Buffer 型の結末) が C11 でも x86 でも到達可能だった。
ただしプロトコルは壊れていない——BOUNDED_WAIT の期限切れ再確認が回復を
担っていて、保証の本体はそちらだった。テストは「見逃し窓が到達可能であり、
かつ期限切れ再確認で必ず回復する」という形に書き換えた。ついでに、全て
SeqCst にしても loom は両者見逃しを出すことも分かった (loom はロケーション
跨ぎの SeqCst 全順序を強制しない)。形式検証の主張は「どのメモリモデルで
何を保証するか」まで書かないと、検証した気になるだけだという教訓。

### 2026-11-09 — Miri が見つけた UB は全部「持ち方」の問題だった

Miri を回したら UB が 3 種類出た。共有領域の base ポインタを読み取り用に
導出していたための Stacked Borrows 違反、1 バイト参照から作った生ポインタ
の provenance 不足 (テスト補助)、そして `Vec<u8>` の画像バッファが 8 バイト
整列しておらず `&AtomicU64` を作ること自体が UB、の 3 つ。どれも実機では
動いてしまう類のもので、テストが全部緑のまま潜んでいた。修正は
SharedRegion を生アロケーション保持に変え、画像バッファは u64 基盤の
整列済み型に置き換えた。同時に layout の公開関数には整列の事前条件を
明記した。「動く」と「正しい」の間に UB 検査を挟む価値は、バグの実在を
突きつけられて初めて実感できる。

### 2026-11-09 — CBMC には CBMC の物差しがある

Kani の harness を増やす作業は、証明の入力範囲との交渉の連続だった。
剰余の証明は u64 全域では 25 分溶けず、幅に依存しない性質だと割り切って
小さくしたら通った。記号長での確保+コピーを含む証明は長さ 4 まで絞っても
解けず、`#[kani::unwind]` で巻き戻し上限 (初期化 32 回 + 回転 4 回 + 余裕)
を宣言したら通った。どちらも「証明を諦める」ではなく「証明可能な形に
性質を切り分ける」話で、大きな入力域は境界テスト・PBT・fuzz が受け持つ、
という役割分担を harness のコメントに残した。形式手法の規模は、正しさの
総量ではなく分担の設計で決まる。

### 2026-11-09 — タイムアウトする mutant は「検出」に入るのか

cargo-mutants の timeout 7 件のうち、経過時間関数を 0 固定にする mutant は
「BOUNDED_WAIT が永遠に期限切れにならない」という意味でテスト群を
ハングさせていた。つまり検出はされているが、形が失敗ではなく停止になる。
CI でミューテーションを回すなら、タイムアウトは kill と同格に扱いつつも
「スイートが固まる」という別種のコストとして記録すべきだと思った。
なお倒せないと判断した mutant の内訳は、Kani 証明本体内 (テストでは
コンパイルされない)、等価 mutant (フラグ合成の `|`→`^` はビットが素で
同値、`1<<0`→`1>>0` は両方 1、等)、そして Drop の中身を消すリーク専用
mutant (単体テストでは観測不能) で、いずれも理由付きで残置した。

### 2026-11-09 — Miri は「遅い」と「通らない」の区別を迫ってくる

spec_table の Miri 未了分 (c01 の 100k 件ループ) を片付けようと、繰り返し
回数を環境変数で絞れるようにした。ところが c01 は OPS=1 でも 100 秒を超え、
OPS=20 では 600 秒で打ち切られ、OPS=200 では 15 分でも終わらない。同じ
バイナリの c03/c14/c15/c17 は約 2 秒で通るし、stacked-borrows を切っても
遅いので、原因は借用追跡でもリング容量でもなさそうだ。手元の仮説は全部
外れた (write/drain は O(1)、セットアップも自明)。ここで大事なのは、
「タイムアウトで打ち切った実行」を「Miri 通過」と数えないことと、「遅い」
を「UB なし」の証拠と取り違えないことだ。絞り込みの仕組み自体は残した
ので、速いマシンか夜間ジョブで回すか、原因を切り分けるかは次の課題として
チェックリスト (D59) に載せた。検証ツールの性能特性も、検証対象の一部だ。

### 2026-11-09 08:29 — Host 検証手順 4 の「確かめる」は、照合相手が要る

A71 の実装で、spec の「コピーした Descriptor の長さ、オフセット、Sequence、
Generation を確かめる」を decode_descriptor だけでは果たせないことがはっきりした。
長さは 1 件だけで判定できるが、Sequence とオフセットは「期待値」が要る。
Sequence は下限照合にした。保存に失敗したイベントにも番号を振る仕様なので、
欠番は正常で、後退だけが矛盾だ。オフセットはもっと強いことが言えた。書き手は
Payload を Descriptor と同じ順に隙間なく確保するので、前件の終端と次件の位置は
完全に一致するはずで、1 バイトのずれも矛盾として止められる。落とした Payload は
格納長 0 として扱うと、位置の再利用も同じ式で説明できる。

判断に迷ったのは Sequence 0 の扱いだ。従来のテストは「未初期化スロット対策」
として 0 を後退検査の対象外にしていた。しかし書き手は 1 から振り、単一公開点の
おかげで write_cursor が進んだスロットが未公開のまま残ることはない。確定済み
スロットの 0 は、write_cursor だけが進んだ壊れた像でしかあり得ない。共有メモリを
信用しない入力として扱うなら、0 を受け入れて偽のイベントを Trace に入れるより、
Ring を止める方が正しい。テストを「拒否する」側に書き換えた。Generation は
Descriptor にフィールドが無く、Control 領域の世代として既に照合済みだった。
仕様の文言をそのまま読むと見落とすが、実装の側から読むと「どこで照合するか」が
決まる、という例だった。

A69 は三値にした。Loader Lock は「保持している」「していない」「分からない」の
三つで、分からないときに 0ms へ切り替える設定を WriterPolicy に用意した。
既定は「分からないときは待たない」。呼び出し側が申告しない限り従来の挙動は
変わらないが、Windows の Agent が DllMain のような曖昧な経路から Unknown を
申告できるようになった。申告の配線自体は Hook 実装時（PoC 第 1 スコープ外）に
接続する。

ついでに i686 の cargo check で、ワークスペース全体では loom-tests 経由の
`generator 0.8.12` が i686 用 asm を持たず失敗することが分かった。自クレートは
問題なく、README の手順どおりの `-p` 指定では両ターゲットとも通る。
依存クレートの都合で CI の i686 ジョブが落ちる罠なので、ジョブ側で loom-tests を
除外するか、generator を避ける構成にする必要がある。stash で変更前の HEAD でも
同じ失敗になることを確認済みで、今回の変更のせいではない。

### 2026-11-09 08:29 — 「c01 が Miri で異常に遅い」は、測り方が間違っていた

D59 の切り分けをサブエージェントに任せたら、根本原因はコードではなく測定方法
だった。Miri は既定でホストの環境変数を解釈対象プログラムへ転送しない
（isolation）。`SHIRUSU_SPEC_TABLE_C01_OPS=1 cargo +nightly miri test` と書いても
変数は届かず、テストは既定の 100,000 件で回っていた。「OPS=1 でも 100 秒超」
は 1 件の遅さではなく 10 万件の重さで、そりゃ終わらない。stacked-borrows を
切っても遅かったのも当然で、仮説の立て方がまるごと的外れだった。

正しい呼び方は `MIRIFLAGS="-Zmiri-env-forward=SHIRUSU_SPEC_TABLE_C01_OPS"` で
変数を明示的に転送すること。これで c01 は OPS=200 で 1.86 秒、c08 は OPS=20 で
0.52 秒で通過し、UB は検出されなかった。spec_table.rs の doc コメントに誤った
呼び方を書いてしまっていたのも直した。教訓は二つある。検証ツールの隔離の
仕組み（Miri の isolation、サンドボックスの環境変数など）は、テストの前提を
黙って変える。そして「遅い」という観測は、まず「本当にその条件で測れているか」
を疑うべきで、条件が届いていない測定の遅さをコードのせいにしてはいけない。
D59 はこれで解決としてチェックリストに記録した。

### 2026-11-09 09:29 — 一時 Payload ID は payload_position で足りていた

overview.md は「Payload には内部転送用の一時的な Payload ID を付ける」と言うのに、
spec の EventDescriptor に ID 用フィールドが無かった（reserved: u64 のみ）。A72 の
決定は「専用フィールドは設けず、`payload_position` を一時 ID として使う」。
書き手が単調に振る論理オフセットで、格納済み Payload は互いに重ならない区間を占める
から、同一 Ring 内では格納済み Payload を一意に識別できる。落とした Payload は
位置を進めないので後続イベントと位置を共有するが、Blob を作らないので ID は不要。
`reserved` は将来の拡張用に 0 のまま残す。`EventDescriptor::temporary_payload_id()`
としてメソッド化し、Ring レベルのテストで格納済み同士の ID が重ならないことと、
落とした件の位置再利用（0, 3, 8, 9, 9）を確認した。フィールドを増やす前に「既存の
単調な値が識別子になっていないか」を疑うのは、64B 固定レイアウトでは特に大事だと感じた。

同じ回で D57（Fuzz で受理したデータの不変条件チェック）をやっていたら、fuzz が
本物の穴を見つけた。`validate_control` は Cursor の後退を前像と照合していたが、
Payload 位置の後退は照合しておらず、後退した像を受理していた。書き手の
payload_write_position は単調にしか進まないのだから、後退は破壊された像として
弾くのが正しい。`validate_control` に前像との Payload 位置の単調性チェックを
追加し、回帰テストを書いた。修正後の fuzz は validate_control で約 1,060 万 runs、
decode_descriptor で約 540 万 runs、decode_payload で約 490 万 runs を
クラッシュなしで通過した。assert を足す作業が、そのままバグ発見になる——これが
verification.md の「クラッシュしないことに加え、受理したデータの不変条件も確かめる」
の意味だったのだと実感した。D53（失敗証跡の回帰テスト化）の観点では、fuzz の
クラッシュ入力は `fuzz/artifacts/` に残るが git 管理外なので、回帰テストとして
validate.rs に同じ条件のテストを残した。
