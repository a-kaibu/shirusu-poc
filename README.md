# shirusu-poc

Trace は `shirusu export capture.trace --format parquet --output events.parquet` で
Parquet に出力できる。DuckDB からの検索とデータの扱いは
[Parquet 出力仕様](docs/parquet-export.md) を参照。

現在の対応範囲は `shirusu capabilities`（機械可読出力は `--json`）で確認できる。
Win32／内部 API は 197 件（生成 L1: 184、手書き: 6、内部: 7）。
32/64bit 整数・短整数・浮動小数点の元の ABI を保って中継する。
COM は Factory の観測と 7,797 IID の名前解決に対応するが、共有オブジェクトの
メソッドを安全に追跡する通常経路は未完成。全 Windows API・COM 対応が完成した
リリースとしては扱わない。検証方法と実動確認の範囲は [docs/verification.md](docs/verification.md) を参照。


shirusu の Agent–Host 転送仕様 v0.4（SPSC Ring と状態遷移）の PoC 実装。
仕様の正は `docs/spec-transport.md`、全体設計は `docs/overview.md`、検証戦略は `docs/verification.md`。
仕様条項・テスト項目と実装の対応は `docs/traceability.md`（網羅チェックリスト、進捗の分母）にあります。

> 範囲について: 最初の実装対象は `shirusu-transport` の SPSC Ring と状態遷移でした（spec.md 末尾の決定）。
> 2026-11-09 の指示で対象はトレーサー全体へ拡大し、Phase 2（公開 Trace への変換）、Phase 3（フック＋レコーダ）、Phase 4（解析 CLI）、Phase 5（ippai 連携基盤）まで実装済みです（いずれもローカル検証のみで、CI 検証はまだです）。
> COMとWinRTはFactory／Activation呼び出しと返却ポインタを記録します。通常の記録では、返されたインターフェイスが他スレッドと共有されていないことを証明できないため、vtableを書き換えず、メソッド記録の不足をCoverageに`shared-object-safety-unproven`として残します。Inline Hookの解除ではトランポリンをプロセス終了まで保持し、再アタッチを含む累積確保試行を4,096回に制限します。Hostへの再接続と予備Queueは初版では扱いません。

## 当初設計との照合（2026年11月13日）

完成条件は [overview](docs/overview.md) の要件に置く。残件は
[completion-plan](docs/completion-plan.md) で追跡し、過去のチェックリストの
「未着手 0」をトレーサー全体の完成とは扱わない。
標準の記録境界は Runtime → Windows API も含む。`--record-runtime-apis` は
Runtime 自身のエクスポートを追加する設定で、CRT 経由の Windows I/O を隠す設定ではない。
全 WinMD の対応状況は `cargo run -p shirusu-metadata-gen -- --inventory target/api-inventory.tsv`
で出力できる。生成可能な型の件数と実機で記録を検証した件数は区別する。

## 2026年11月12日のレビュー対応

WinRT検証アプリのリンク先を、[RoActivateInstanceの指定](https://learn.microsoft.com/en-us/windows/win32/api/roapi/nf-roapi-roactivateinstance)に従って`RuntimeObject.lib`へ変更しました。
Microsoft署名の判定では、成功したWinVerifyTrustの状態から署名者証明書を取得し、状態を閉じる前に組織名を確認します。
埋め込み署名が確認できない場合はSHA256とSHA1のカタログを検索し、対象ファイルのハッシュに対する所属と信頼性を検証します。
署名のないファイル、変更されたファイル、確認に失敗したファイルはMicrosoft製と分類しません。

Metadata Generatorは、void、32bit整数、ポインタ幅整数、ポインタの引数と戻り値を区別したWrapperを生成します。
元APIもその関数型で呼び出し、記録用の整数表現への変換は呼び出しの前後だけで行います。
32bit未満の整数、固定64bit整数、浮動小数点数など、現在の生成器でABIを保持できない型は見送ります。

WndProcの読み戻しにはGetWindowLongPtrとGetClassLongPtrのA/W版を追加し、既知のWrapperを元のプロシージャへ解決します。
x86ではPtr版がマクロであるため、対応するLong版をフックします。
現在の検証範囲は、登録、同じプロシージャへの差し替え、ウィンドウとクラスからの読み戻しです。
GetClassInfo経由の読み戻し、A/W間の変換Thunk、解除後に存続するウィンドウまで含めた透過性は未保証です。

回帰テストでは、解除後に取得済みトランポリンを呼ぶケース、COMメソッドの並行実行中にvtableを変更しないこと、生成Wrapperのvoid／整数／ポインタ戻り値、Coverageの不足理由のTraceへの保存を検査します。
Inline Hookのスレッド停止方式は、新規スレッドの生成や停止先が保持するロックまで制御するものではありません。
これらのテストの通過を、任意の既存プロセスへの安全なAttachの保証として扱わないでください。

転送の核となる契約は 1 つです。

- 書き手: Payload コピー → Descriptor 書込 → `write_cursor` を Release 更新（公開点はここだけ）
- 読み手: `write_cursor` を Acquire → 確定分だけコピー → 検証 → `read_cursor` / `payload_read_position` を Release 更新

通常経路ではプロセス共通ロックも全順序フェンスも使いません。満杯時は既定 1ms まで待って
OVERFLOW に入り、まず Payload だけ落として Descriptor を残し、それも無理ならイベントを捨てて
Loss カウンタと Sequence 欠番で欠落を残します。

## 使い方

```bash
# ビルドとテスト (Linux/macOS でも transport の核は動く)
cargo test --workspace
cargo test -p shirusu-loom-tests

# Windows ターゲットのコンパイル確認 (Linux から)
cargo check -p shirusu-transport-win -p shirusu-agent -p shirusu-host -p shirusu-trace --target x86_64-pc-windows-msvc
cargo check -p shirusu-transport-win -p shirusu-agent -p shirusu-host -p shirusu-trace --target i686-pc-windows-msvc

# E2E シナリオ (プロセス内 + 子プロセス起動スモーク)
cargo build --workspace
./target/debug/shirusu-e2e-supervisor --all
# Windows: x86 producer + x64 host のプロセス間実テスト
#   $env:SHIRUSU_E2E_PRODUCER = "target\i686-pc-windows-msvc\debug\shirusu-e2e-producer.exe"
#   .\target\x86_64-pc-windows-msvc\debug\shirusu-e2e-supervisor.exe --cross-arch
#   .\target\x86_64-pc-windows-msvc\debug\shirusu-e2e-supervisor.exe --memory-order-stress
```

CI と同じ手順は `scripts/ci/` にあります（`linux.sh` / `windows.ps1` / `windows-x86.ps1` /
`kani.sh` / `fuzz-short.sh` / `tla.sh`）。GitHub Actions の定義は `.github/workflows/` です。

CIは同じrefとスイートの最新実行だけを残し、新しいpushや同じスイートの手動実行で古い実行をキャンセルします。
定期実行と長時間検証のスイートは通常のCIと別に管理します。
集約ジョブは失敗を報告しますが、キャンセル後には起動しません。
Rustの依存キャッシュはジョブとツールチェーンごとに分け、mainでは後続テストが失敗した場合にも保存します。
通常のワークスペースに加えてfuzzの依存ビルドとKaniの導入先を保存し、WinMDとTLA+ツールは取得スクリプトのハッシュをキーに再利用します。
TLA+だけを実行するジョブではRustのセットアップとRustキャッシュの復元を行いません。

## 調整値の測定による決定 (A73)

spec 冒頭「リングの容量、Slot 数、待機上限、復帰の閾値は測定で調整する
値であり、変えても安全性やイベントの意味は変わらない」に対応する測定。
ベンチは `e2e/src/bin/shirusu-tuning-bench.rs`（A65 の wait-bench と同じ流儀）。

- 環境: Linux VM（4 CPU、約 8GB）、`cargo run --release -p shirusu-e2e --bin shirusu-tuning-bench -- --rounds 3`。
  3 回実行し、同じ傾向を確認した（数値は 2 回目の中央値。S1/S2/S4/S5 は
  3 回とも概ね 10% 以内で一致。S3 の検出遅延だけ到着位相のランダム化の
  ため実行ごとに 2〜3 割程度ばらつくが、区間の半分に沿う序列は 3 回とも同じ）。
  Windows 実機での数値は CI 待ち。
- S1 の consumer は検証なし RingReader を使う。検証付き DrainWorker は
  回収のたびに像全体をコピーする（D65）ため、容量が大きいほど回収コスト
  が増える——それは容量そのものの効果ではなく検証経路のコストなので、
  容量の掃引からは分離した。この像コピーコスト自体は、Ring を大きくし
  すぎない理由の一つでもある（下記「維持」の根拠）。
- S1b の producer は「書けるだけ書く」ため、欠落率の高さは実運用の損失
  率ではない（実 Hook の発生頻度はこの測定の数百万件/秒には遠く及ばない）。
  比較の意味があるのは同じ offered load での構成間の Published 件数である。

### S1a: Ring 容量 × スループット（consumer は 200µs 周期で回収、50,000 件 × 256B）

|---|---|---|---|---|
| 256 | 256KiB | 272KiB | 約 0.89M | 0 |
| 1024 | 256KiB | 320KiB | 約 2.74M | 0 |
| 4096 | 256KiB | 512KiB | 約 2.67M | 0 |
| 16384 | 256KiB | 1280KiB | 約 2.40M | 0 |
| 256 | 1MiB | 1040KiB | 約 0.87M | 0 |
| 1024 | 1MiB | 1088KiB | 約 2.78M | 0 |
| **4096** | **1MiB（本番既定）** | **1280KiB** | **約 5.70M** | **0** |
| 16384 | 1MiB | 2048KiB | 約 6.04M | 0 |
| 256 | 4MiB | 4112KiB | 約 0.88M | 0 |
| 1024 | 4MiB | 4160KiB | 約 2.79M | 0 |
| 4096 | 4MiB | 4352KiB | 約 5.80M | 0 |
| 16384 | 4MiB | 5120KiB | 約 6.55M | 449 件（0.9%、1 ラウンドのみの外れ値） |

スループットは descriptor 容量ではなく実効深さ `min(descriptor 容量, payload 容量 / 平均 Payload 長)`
で決まる。256KiB payload では 256B/件で最大 1024 件しか入らず、descriptor を
1024 → 16384 に増やしても伸びない（2.4〜2.8M/s で頭打ち。1 回目の 4096 件
2.41M/s に対する 1024 件 2.80M/s の逆転は 2 回目で解消し、ノイズと判断）。
本番既定（4096 件 / 1MiB、実効深さ 4096）は約 5.7M/s で、256 件構成の約 6.5 倍、
1024 件構成の約 2.1 倍。16384 件 / 4MiB は約 6.6M/s とさらに伸びるが、
共有メモリ 4 倍（1280KiB → 5120KiB）に対して +15% 程度でしかない。

|---|---|---|---|---|---|
| 256 | 256KiB | 約 6.96M | 約 91k | 1 | 約 6.87M（98.7%） |
| 1024 | 256KiB | 約 6.94M | 約 359k | 2 | 約 6.58M（94.8%） |
| 4096 | 256KiB | 約 0.39M | 約 391k | 1540 | 0（0%） |
| 16384 | 256KiB | 約 0.40M | 約 395k | 1542 | 0（0%） |
| 256 | 1MiB | 約 7.27M | 約 89k | 1 | 約 7.18M（98.8%） |
| 1024 | 1MiB | 約 7.69M | 約 354k | 2 | 約 7.34M（95.4%） |
| **4096** | **1MiB（本番既定）** | **約 7.36M** | **約 1.38M** | **1** | **約 5.99M（81.3%）** |
| 16384 | 1MiB | 約 1.48M | 約 1.48M | 1397 | 0（0%） |
| 256 | 4MiB | 約 7.43M | 約 93k | 3 | 約 7.34M（98.8%） |
| 1024 | 4MiB | 約 7.52M | 約 366k | 2 | 約 7.16M（95.1%） |
| 4096 | 4MiB | 約 7.93M | 約 1.39M | 2 | 約 6.54M（82.4%） |
| 16384 | 4MiB | 約 9.18M | 約 4.55M | 3 | 約 4.63M（50.4%） |

ここで欠落率の差には仕組みがある。payload 容量が先に尽きる構成
（payload 容量 / 256B < descriptor 容量）では、書き手は 1ms の
BOUNDED_WAIT に入って Host の回収を待つため、attempted 自体が抑えられ
欠落はほぼ 0 になる（4096 件 / 256KiB、16384 件 / 1MiB など）。一方
descriptor と payload が同時に尽きる構成（4096 件 / 1MiB など）では
descriptor 空きが無くなり、書き手は待たずに高速で欠落させる。
Published 件数は実効深さにほぼ比例して伸びる（256 件で約 90k →
4096 件 / 1MiB で約 1.38M → 16384 件 / 4MiB で約 4.55M）。本番既定は
5ms 周期の遅い Host でも約 690k 件/秒を通す。欠落率 81% という数字は
producer が 3.6M 件/秒で書き続けた場合のもので、実運用の目安ではない。

### S2: BOUNDED_WAIT 上限（Host が書き手の待機確認から 500µs 後に回収、25 ラウンド）

| max_wait | 再開できた | 再開遅延（中央値 / p95） | 書き手の待機時間（中央値） |
|---|---|---|---|
| 0 | 0/25 | —（待たない） | 0 |
| 0.25ms | 0/25 | —（回収前に期限切れ） | 0 |
| **1ms（既定）** | **25/25** | **68µs / 87µs** | **643µs** |
| 5ms | 25/25 | 72µs / 92µs | 643µs |

Host が 30ms 回収しない場合の、満杯への 1 回の書込の停滞時間（中央値、10 ラウンド）:
0 → 0µs、0.25ms → 313µs、1ms → 1057µs、5ms → 5056µs。
上限ちょうど + 約 57µs（50µs スライス + スケジューリング）で返る。
1ms は 500µs の Host 遅延を 2 倍の余裕で吸収し、5ms は Host が速い
場合の再開遅延が 1ms と同じ（72µs 対 68µs）で、Host が止まった場合の
停滞だけが 5 倍になる。0.25ms は 500µs の遅延に間に合わず全滅する。

### S3: 再確認周期（通知を取りこぼし、データ到着は 1〜21ms でランダム化、25 ラウンド）

| interval | 検出遅延（中央値 / p95） | アイドル時の再確認回数（/100ms） |
|---|---|---|
| 1ms | 648µs / 1210µs | 96 回（約 960 回/秒） |
| **2ms（既定）** | **1506µs / 2136µs** | **51 回（約 510 回/秒）** |
| 5ms | 2151µs / 5222µs | 22 回（約 220 回/秒） |
| 10ms | 4588µs / 9360µs | 12 回（約 120 回/秒） |

検出遅延の中央値はおおむね区間の半分（+ 起床オーバーヘッド）で、区間を
短くするほど検出は速くなるが、アイドル時の wakeup が比例して増える。
2ms は検出遅延の中央値 1.5ms に対して wakeup 約 510 回/秒。1ms にすると
検出は約 0.65ms まで速くなるが wakeup は約 960 回/秒とほぼ倍になる。
（1 回目の測定では到着時刻を 7ms 固定にしており、5ms/10ms が同じ再確認
境界に当たって区間の差が出なかったため、到着時刻をランダム化して測り直した）

なお、2ms は再確認の周期であり回収の上限ではない。待機が終わった後にすぐ
実行されるとは限らないため、2ms 以内の回収は保証しない（p95 2136µs のとおり、
2ms を超える検出遅延も起き得る）。利用側は 2ms 以内の回収を前提にしないこと。

### S4: 復帰閾値（16 件 Ring、Payload 256B/件、決定的測定）

| 復帰閾値 | OVERFLOW から復帰に必要なまとまった回収件数 | 復帰後の headroom（再 OVERFLOW までの Published 数） |
|---|---|---|
| 25% | 13 件 | 12 件 |
| **50%（既定）** | **9 件** | **8 件** |
| 75% | 5 件 | 4 件 |

25% は復帰が遅く（16 件中 13 件の回収が必要）、75% は早く復帰するが
復帰後わずか 4 件で再 OVERFLOW する（フラッピング）。50% は中間で、
9 件の回収で復帰し 8 件の余裕がある。なお、1 件ずつ小刻みに回収して
書く、を繰り返しても 32 回以内ではどの閾値でも復帰しなかった。
OVERFLOW 中は劣化 Descriptor が空いた枠を即座に埋め戻すため、復帰には
使用率が閾値を下回るだけの「まとまった」回収が必要、という実装の性質
そのものが測れた。

### S5: Slot 数・低水位

- 1 Slot あたり 1,310,976 バイト（1280KiB。本番既定 Ring 1 本分）。
  32 スロットの Pool 全体で 41,951,232 バイト（40.0MiB）。
- 32 スロットの claim は 8〜31µs（2 回の測定値。どちらも無視できる速さ）。
- 拡張要求の発火点は設計どおり: 24 件 claim（空き 8 件）では要求 0 回、
  25 件 claim（空き 7 件）で要求 1 回。低水位 8 は「空きが 8 件を切ったら」
  要求を立てる、という意味で、発火後に残る空きは 7 件分ある。

## 実装して感じたこと

作業の節目ごとに追記しています（後付けの作文ではなく、その時点で気づいたこと）。

### 2026-11-09 00:31 — Descriptor を 64B に詰める理由は「検証の単位」だった

仕様の表だけ見ると 64B はキャッシュラインへの配慮に見えるが、実装してみると意味が違った。
Descriptor がちょうど 1 キャッシュライン = 固定 64B だと、Host 検証は「64B をコピーしてから
検証する」が機械的に書ける。サイズが可変だったら、検証前のコピー自体が入力依存になって
しまう。レイアウトの静的アサーション（offset_of まで全部止める）は、x86/x64 混在のためと
いうより、将来フィールドを足したくなったときに必ず誰かが気づくための柵だと感じた。

### 2026-11-09 00:38 — 通知の取りこぼしは「正しさ」ではなくコスト配分の問題

v0.1 方式が Release/Acquire で動かない理由をコードに落とすと、結局「全順序フェンスを
毎イベント打つか、2ms の再確認で諦めるか」の配分でしかない。フェンスを通常経路に入れない
設計は、コードでは「notify モジュールが順序付けを一切触らない」という形にすると一番
素直だった。閾値越え通知も、ラッチを持たせないと「越えている間ずっと SetEvent する」
素朴な実装になりがちで、テストで初めて気づいた。

### 2026-11-09 00:41 — Payload 先落としは割り切りだが、L1 の線引きが救いになる

Overflow で Payload だけ落とす判断は、実装すると「Descriptor は残るのに中身が無い」
という中途半端な状態をたくさん作る。救いなのは、落とした理由を値ごとに残し、
「Payload を落とした呼出は L1 として扱わない」を型（CaptureState）で表せること。
この線引きが無いと、下流が骨格だけのイベントを完全な記録と誤認する。逆に言うと、
この割り切りは Host 側の完全性報告まで実装して初めて成立する。片方だけでは嘘になる。
なお予備 Queue を捨てた判断（v0.4）にも同意する。実装を考えると、Queue は「もう 1 本
Ring を作る」のと同じだけの検証対象を増やすのに、得られるのは Slot 不足の緩和だけだった。

### 2026-11-09 00:47 — Host が共有メモリを信用しない代償は「二重の簿記」

検証モジュールを作ると、Host は Cursor・世代・カウンタの全部について「前回値」を
自分側に持つ必要が出てくる。共有メモリの値を読むだけの素朴な Host の倍の状態量になる。
それでも、検証の順序（世代 → Cursor 後退 → カウンタ）を間違えると、別 Ring の像を
「Cursor が後退した破損」と誤判定することをテストで踏んだ。誤判定は「止めるべきでない
Ring を止める」方向のバグで、検出漏れより実害が大きい場面があると思う。

### 2026-11-09 00:55 — ストレステストの設計ミスは、製品のバグより先にテストが嘘をつく

SPSC 並行テストで、劣化イベントを正常件数に数えたため reader が早期終了し、
producer が空転してテストがハングした。製品側の契約（劣化は公開だが正常ではない）を
テストが正確に写せていなかった。100k 件の数字だけ大きくしても、数え方を間違えると
検証にならない。「何を 1 件と数えるか」は転送の意味論そのものだと実感した。

### 2026-11-09 01:02 — loom と実プロセスの差は、loom が正しいほど気になる

loom のモデルは公開/回収の順序を網羅してくれるが、モデルの Ring は自分で書いた
最小版なので、「実装の写し絵を検査している」危険が常にある。参照モデルと実装を
独立させるという test.md の注意は PBT だけでなく loom にも効く。実プロセス間
（File Mapping、Handle 寿命、プロセス終了）は loom では一切見えないので、
Windows E2E を CI で実走させることに意味がある。逆に、CI でしか見えない失敗を
ローカルの loom/PBT に還元できる形（同期ポイント、仮想時計）で E2E を書くべきだった。

### 2026-11-09 01:16 — TLA+ の状態爆発は「無制限な Generation」が起こしていた

TLC が終わらなかった原因は Ring ではなく Slot の Generation だった。Claim/Reclaim の
サイクルは Cursor を進めずに Generation だけ増やせるので、状態空間が無限に伸びる。
制約に Generation <= 2 を入れたら 12 秒で終わった。「再利用を 1 回だけ許す」モデルでも
不変条件の検査としては十分で、境界をどこに引くかはモデルの設計そのものだと分かった。
Kani のセットアップが tar の所有権で落ちた件も含め、検証ツールは「導入できるか」が
最初の関門で、CI 側のスクリプトに回避策 (TAR_OPTIONS) を残す価値があった。

### 2026-11-09 01:39 — チェックリスト自体に漏れがある。仕様の再読が分母を増やす

実装が一通り終わった後に spec を条項ごとに読み直したら、チェックリストに無い
仕様が 5 つ出てきた。空き待ち経路の全順序フェンス（A61）、共有メモリセクションの
アクセス制御（A62）、Slot Pool の総メモリ上限（A63）、Host 突然終了時の
Finalization 不在の扱い（A64）、待機方式のベンチマーク選定（A65）。A61〜A64 は
この場で実装し、ローカルテストまで通した。A65 はベンチマークハーネスが無いので
未着手のまま残す。分母は 135→140 に増えた。
教訓は二つ。ひとつは「全部実装した」という感覚はチェックリストの完全性に依存
していて、チェックリスト自体が間違うこと。もうひとつは、仕様の文は「〜する」
と「〜できるようにする」を混ぜて書くので、後者（上限の設定可能性など）は
実装の有無を判定しにくく、見落としやすいこと。フェンスの件は、待機が
ポーリング実装だと動いてしまうためテストが無ければ気づかない類の抜けで、
フラグを消すミューテーションでスレッドテストが落ちることを確認してから
採用した。ACL は Windows でしか動かず、ローカルでは cargo check までしか
確認できない。こういう項目は CI が通るまで「実装済み未検証」のまま置くのが正しい。

大きな Snapshot の Fragment 取得中に元メモリが変わり得る問題は、文書に一行書くだけなら
読み手が忘れる。`SnapshotOutcome.simultaneity_guaranteed: false` のように結果の型に
必ず現れる形にすると、使う側が握りつぶしにくい。保証しないものを「しない」と
表明するフィールドは無駄に見えて、表明し忘れを防ぐ柵になる。

### 2026-11-09 01:45 — 配布経路の都合が、テスト資産の保持形式を決めた

fuzz の種はバイナリであることが本質だが、このリポジトリへの push 経路
（GitHub API のスナップショット）が UTF-8 テキストしか運べず、バイナリ種を
含む push は全体が拒否された。そこで正の種を hex テキストで保持し、
`corpus/` は生成物に格下げした。検証資産の形式は「検査に最適か」だけでなく
「配布・保存の経路を通るか」でも決まる。往復のハッシュ一致を確認してあるので
情報は落としていないが、経路の制約が設計に漏れ込む好例になった。

### 2026-11-09 02:52 — 通知の結線は「部品がある」だけでは終わらない

A61 の空き待ちフェンスと通知は、ライブラリ単位では `drain_*_with_space_notify`
にクロージャを渡す形で揃っていた。しかし Host プロセスが毎回同じ結線を書く
設計だと、書き忘れがそのまま通知欠落になる。結線を `NotifyingDrainWorker`
に集約して、回収と `space_available` の SetEvent を 1 か所で結んだ。
E2E シナリオでは書き手を 3 回待機に入れて、通知がちょうど 3 回飛び、欠落なく
16 件が再開することを確認した。通知回数が待機エピソードと一致するのは、
「回収した分だけ・待っているときだけ」通知できている証拠で、回数そのものが
仕様の確認になっている。`space_notifications` のようなカウンタは、デバッグ用
というより「通知が仕様通りの回数だけ飛んだか」を数えるためのものだと気づいた。

### 2026-11-09 02:52 — 待機方式は Event に決まったが、収穫はスタブの嘘に気づいたこと

ベンチ（50 ラウンド）では Event が中央値 14µs / p95 24µs で、sleep 方式の
中央値 48µs / p95 97µs を上回った。sleep の p95 に 1ms 超の外れがあったのは、
スリープの粒度がスケジューラに左右される尾のリスクで、イベント方式が尾も
抑える。数字より収穫だったのは、Linux スタブの EventObject が 1ms ポーリング
だったことに気づいたことだ。スタブのまま EventClock を作っても、Linux では
sleep 方式より遅くなり、ベンチの数字が嘘になる。condvar ベースの真の
ブロッキング待機に書き換えたら、イベント方式の待機ループ回数は sleep の
約 1/10 になった。スタブは「API 形だけ保つ」つもりでも、タイミングの意味論
まで似せないと計測が成立しない。残りは Agent が Host から space_available
ハンドルを受け取る受け渡し（A68）で、ここはプロセス間の設計が要る。

### 2026-11-09 03:29 — 受け渡しは「ハンドルを渡す」だけでは終わらない。使う側の Clock まで差し替える

A68 で Host→Agent の `space_available` 受け渡しを実装した。`EventObject` に
`DuplicateHandle` 経路が無かったので、まずそこから作った。`SharedMapping` の
複製と並べると、Event の複製は Handle の寿命の扱いだけが違う（複製した
ハンドルから作った `EventObject` を Drop すれば複製側が閉じる）。Agent 側は
ハンドル値から `RingNotify` を作り、`EventClock` を Clock として差し替える
`attach_space_available` を用意した。ここで気づいたのは、Agent の Clock が
`thread_begin` の時点で書き手に複製されるため、受け取りが遅れると既存の
書き手が古い Clock を掴んだままになることだ。差し替えは書き始め前に限る
（遅れたら `None` を返す）という制約を、便利さより正しさで選んだ。
受け渡しの実証は 2 段にした。Windows 実機では自プロセスへの複製で SetEvent
が複製側から観測できるテスト（GHA で回る）。Linux ではプロセス内共有の
同じ `Arc<RingNotify>` で Agent と Host を結び、E2E で書き手が EventClock
で待機したこと（`sleep_calls() > 0`）を確認する。ミューテーション確認では
Clock の差し替えを外すと E2E が `event_waits=0` で落ち、他の観測は全て
通った。シナリオが「ハンドルが渡ったか」ではなく「渡った先で待機に使われたか」
を見ている証拠になる。残る未着手は D41 の CI フィードバックループのみで、
それは一括 push と kota の判断を待つ。

### 2026-11-09 — 「テストが足らない」は測定したら本当だった

「全然テストが足らない」という指摘を受けてカバレッジを測ったら、全体で
71% しかなく、最悪の crc32c は 67% だった。面白いのは未達行の顔ぶれで、
`make_table` の本体——CRC テーブルを生成する const fn そのもの——が丸ごと
未実行だった。実行時にテーブルを参照するテストは幾らでもあるのに、生成は
コンパイル時に終わっているから、誰も「実行した」ことにならない。対策は
const 版と実行時版 (ビット演算リファレンス) の差分照合で、カバレッジと
正しさの両方を一度に取れた。ミューテーションも同じ構図で、88 件のテストが
554 件の mutant のうち 75 件を取りこぼし、その多くは「値を返すだけの
アクセサ (容量・空き数・次シーケンス覗き見) を誰も直接 assert していない」
という地味な穴だった。テストの「件数」は安心感をくれるが、効いているかは
別の物差しが要る、という当たり前を数字で殴られた回。

### 2026-11-09 — 損失の「見え方」は観測点で違う

損失会計の保存則プロパティを書くとき、公開数 = 受信数 + 損失数の等式が
末尾のドロップで崩れて何度か悩んだ。理由は単純で、シーケンス欠番として
観測できる損失は「その後に受信できたイベント」があって初めて姿を現す。
末尾で落ちたイベントは欠番にはならず、カウンタの中にだけいる。つまり
「欠番の合計」と「ドロップカウンタ」は別の観測量で、突き合わせるなら
総和側で閉じる式にしないといけない。100 万イベントのソークではこの形で
完全一致した (受信 64,201 + 損失 935,799 = 1,000,000)。会計の式は
仕様の文面より先に「何で観測するか」を決めないと書けない。

### 2026-11-09 — Dekker のつもりが Store Buffer だった

通知の lost-wakeup を loom でモデル化したら、厳密な Dekker 式の主張
(「両者が互いを見逃すことはない」) が普通に反例を出した。実装の順序付けは
Release ストア + Acquire ロード + 片側だけの SeqCst フェンスで、この組合せ
では両者見逃し (Store Buffer 型の結末) が C11 でも x86 でも到達可能だった。
ただしプロトコルは壊れていない——BOUNDED_WAIT の期限切れ再確認が回復を
担っていて、保証の本体はそちらだった。テストは「見逃し窓が到達可能であり、
かつ期限切れ再確認で必ず回復する」という形に書き換えた。ついでに、全て
SeqCst にしても loom は両者見逃しを出すことも分かった (loom はロケーション
跨ぎの SeqCst 全順序を強制しない)。形式検証の主張は「どのメモリモデルで
何を保証するか」まで書かないと、検証した気になるだけだという教訓。

### 2026-11-09 — Miri が見つけた UB は全部「持ち方」の問題だった

Miri を回したら UB が 3 種類出た。共有領域の base ポインタを読み取り用に
導出していたための Stacked Borrows 違反、1 バイト参照から作った生ポインタ
の provenance 不足 (テスト補助)、そして `Vec<u8>` の画像バッファが 8 バイト
整列しておらず `&AtomicU64` を作ること自体が UB、の 3 つ。どれも実機では
動いてしまう類のもので、テストが全部緑のまま潜んでいた。修正は
SharedRegion を生アロケーション保持に変え、画像バッファは u64 基盤の
整列済み型に置き換えた。同時に layout の公開関数には整列の事前条件を
明記した。「動く」と「正しい」の間に UB 検査を挟む価値は、バグの実在を
突きつけられて初めて実感できる。

### 2026-11-09 — CBMC には CBMC の物差しがある

Kani の harness を増やす作業は、証明の入力範囲との交渉の連続だった。
剰余の証明は u64 全域では 25 分溶けず、幅に依存しない性質だと割り切って
小さくしたら通った。記号長での確保+コピーを含む証明は長さ 4 まで絞っても
解けず、`#[kani::unwind]` で巻き戻し上限 (初期化 32 回 + 回転 4 回 + 余裕)
を宣言したら通った。どちらも「証明を諦める」ではなく「証明可能な形に
性質を切り分ける」話で、大きな入力域は境界テスト・PBT・fuzz が受け持つ、
という役割分担を harness のコメントに残した。形式手法の規模は、正しさの
総量ではなく分担の設計で決まる。

### 2026-11-09 — タイムアウトする mutant は「検出」に入るのか

cargo-mutants の timeout 7 件のうち、経過時間関数を 0 固定にする mutant は
「BOUNDED_WAIT が永遠に期限切れにならない」という意味でテスト群を
ハングさせていた。つまり検出はされているが、形が失敗ではなく停止になる。
CI でミューテーションを回すなら、タイムアウトは kill と同格に扱いつつも
「スイートが固まる」という別種のコストとして記録すべきだと思った。
なお倒せないと判断した mutant の内訳は、Kani 証明本体内 (テストでは
コンパイルされない)、等価 mutant (フラグ合成の `|`→`^` はビットが素で
同値、`1<<0`→`1>>0` は両方 1、等)、そして Drop の中身を消すリーク専用
mutant (単体テストでは観測不能) で、いずれも理由付きで残置した。

### 2026-11-09 — Miri は「遅い」と「通らない」の区別を迫ってくる

spec_table の Miri 未了分 (c01 の 100k 件ループ) を片付けようと、繰り返し
回数を環境変数で絞れるようにした。ところが c01 は OPS=1 でも 100 秒を超え、
OPS=20 では 600 秒で打ち切られ、OPS=200 では 15 分でも終わらない。同じ
バイナリの c03/c14/c15/c17 は約 2 秒で通るし、stacked-borrows を切っても
遅いので、原因は借用追跡でもリング容量でもなさそうだ。手元の仮説は全部
外れた (write/drain は O(1)、セットアップも自明)。ここで大事なのは、
「タイムアウトで打ち切った実行」を「Miri 通過」と数えないことと、「遅い」
を「UB なし」の証拠と取り違えないことだ。絞り込みの仕組み自体は残した
ので、速いマシンか夜間ジョブで回すか、原因を切り分けるかは次の課題として
チェックリスト (D59) に載せた。検証ツールの性能特性も、検証対象の一部だ。

### 2026-11-09 08:29 — Host 検証手順 4 の「確かめる」は、照合相手が要る

A71 の実装で、spec の「コピーした Descriptor の長さ、オフセット、Sequence、
Generation を確かめる」を decode_descriptor だけでは果たせないことがはっきりした。
長さは 1 件だけで判定できるが、Sequence とオフセットは「期待値」が要る。
Sequence は下限照合にした。保存に失敗したイベントにも番号を振る仕様なので、
欠番は正常で、後退だけが矛盾だ。オフセットはもっと強いことが言えた。書き手は
Payload を Descriptor と同じ順に隙間なく確保するので、前件の終端と次件の位置は
完全に一致するはずで、1 バイトのずれも矛盾として止められる。落とした Payload は
格納長 0 として扱うと、位置の再利用も同じ式で説明できる。

判断に迷ったのは Sequence 0 の扱いだ。従来のテストは「未初期化スロット対策」
として 0 を後退検査の対象外にしていた。しかし書き手は 1 から振り、単一公開点の
おかげで write_cursor が進んだスロットが未公開のまま残ることはない。確定済み
スロットの 0 は、write_cursor だけが進んだ壊れた像でしかあり得ない。共有メモリを
信用しない入力として扱うなら、0 を受け入れて偽のイベントを Trace に入れるより、
Ring を止める方が正しい。テストを「拒否する」側に書き換えた。Generation は
Descriptor にフィールドが無く、Control 領域の世代として既に照合済みだった。
仕様の文言をそのまま読むと見落とすが、実装の側から読むと「どこで照合するか」が
決まる、という例だった。

A69 は三値にした。Loader Lock は「保持している」「していない」「分からない」の
三つで、分からないときに 0ms へ切り替える設定を WriterPolicy に用意した。
既定は「分からないときは待たない」。呼び出し側が申告しない限り従来の挙動は
変わらないが、Windows の Agent が DllMain のような曖昧な経路から Unknown を
申告できるようになった。申告の配線自体は Hook 実装時（PoC 第 1 スコープ外）に
接続する。

ついでに i686 の cargo check で、ワークスペース全体では loom-tests 経由の
`generator 0.8.12` が i686 用 asm を持たず失敗することが分かった。自クレートは
問題なく、README の手順どおりの `-p` 指定では両ターゲットとも通る。
依存クレートの都合で CI の i686 ジョブが落ちる罠なので、ジョブ側で loom-tests を
除外するか、generator を避ける構成にする必要がある。stash で変更前の HEAD でも
同じ失敗になることを確認済みで、今回の変更のせいではない。

### 2026-11-09 08:29 — 「c01 が Miri で異常に遅い」は、測り方が間違っていた

D59 の切り分けをサブエージェントに任せたら、根本原因はコードではなく測定方法
だった。Miri は既定でホストの環境変数を解釈対象プログラムへ転送しない
（isolation）。`SHIRUSU_SPEC_TABLE_C01_OPS=1 cargo +nightly miri test` と書いても
変数は届かず、テストは既定の 100,000 件で回っていた。「OPS=1 でも 100 秒超」
は 1 件の遅さではなく 10 万件の重さで、そりゃ終わらない。stacked-borrows を
切っても遅かったのも当然で、仮説の立て方がまるごと的外れだった。

正しい呼び方は `MIRIFLAGS="-Zmiri-env-forward=SHIRUSU_SPEC_TABLE_C01_OPS"` で
変数を明示的に転送すること。これで c01 は OPS=200 で 1.86 秒、c08 は OPS=20 で
0.52 秒で通過し、UB は検出されなかった。spec_table.rs の doc コメントに誤った
呼び方を書いてしまっていたのも直した。教訓は二つある。検証ツールの隔離の
仕組み（Miri の isolation、サンドボックスの環境変数など）は、テストの前提を
黙って変える。そして「遅い」という観測は、まず「本当にその条件で測れているか」
を疑うべきで、条件が届いていない測定の遅さをコードのせいにしてはいけない。
D59 はこれで解決としてチェックリストに記録した。

### 2026-11-09 09:29 — 一時 Payload ID は payload_position で足りていた

overview.md は「Payload には内部転送用の一時的な Payload ID を付ける」と言うのに、
spec の EventDescriptor に ID 用フィールドが無かった（reserved: u64 のみ）。A72 の
決定は「専用フィールドは設けず、`payload_position` を一時 ID として使う」。
書き手が単調に振る論理オフセットで、格納済み Payload は互いに重ならない区間を占める
から、同一 Ring 内では格納済み Payload を一意に識別できる。落とした Payload は
位置を進めないので後続イベントと位置を共有するが、Blob を作らないので ID は不要。
`reserved` は将来の拡張用に 0 のまま残す。`EventDescriptor::temporary_payload_id()`
としてメソッド化し、Ring レベルのテストで格納済み同士の ID が重ならないことと、
落とした件の位置再利用（0, 3, 8, 9, 9）を確認した。フィールドを増やす前に「既存の
単調な値が識別子になっていないか」を疑うのは、64B 固定レイアウトでは特に大事だと感じた。

同じ回で D57（Fuzz で受理したデータの不変条件チェック）をやっていたら、fuzz が
本物の穴を見つけた。`validate_control` は Cursor の後退を前像と照合していたが、
Payload 位置の後退は照合しておらず、後退した像を受理していた。書き手の

クラッシュ入力は `fuzz/artifacts/` に残るが git 管理外なので、回帰テストとして
validate.rs に同じ条件のテストを残した。

### 2026-11-09 10:10 — 一時 ID は「転送の都合」ではなく「Host の簿記」だった

09:29 の所感で「一時 Payload ID は payload_position で足りていた」と書いたが、
kota の指摘で設計を修正した。`sequence + payload_position` は同一 Ring の
中では一意でも、Capture 全体では一意でない。別の Ring が同じ値を出し得るし、
Ring を再利用すれば Sequence も位置も振り直される。「格納済み同士で重ならない」
のは転送レベルの性質であって、識別子の設計としては Host が管理する要素が
足りていなかった。

確定した仕様は「Payload は Agent–Host 間で独立した ID を持たない」。
Agent は格納位置と長さを渡すだけにし、Host が回収時に
`TemporaryPayloadKey { process_id, ring_id, generation, sequence, payload_position }`
を生成する。ring_id と generation は Host 管理の値で、EventDescriptor の
64B レイアウトも `reserved = 0` の検証も変えていない。旧
`EventDescriptor::temporary_payload_id()` は「Descriptor 単体から ID が決まる」
という誤った形だったので撤去した。欠落した Payload にはキーを作らず、
欠落理由は Loss 側に残る。

検証は Unit（要素を 1 つずつ変えてキーが変わること、欠落時に生成されない
こと、再利用時に衝突しないこと）に加え、PBT/DST で「複数 Ring・再利用・
位置の折り返しを含む列で、発行済みキーが全体で一意であり、古いキーが
再利用後の新しい Payload を指さない」ことを参照モデルと照合した。
09:29 の判断自体は当時の情報では筋が通っていたが、「一意である範囲を
どこまで要求するか」を決めるのは設計側の責任で、テストの都合で決めては
いけなかった、というのが今回の収穫。

### 2026-11-09 — テスト拡充第2弾: 件数は「行列の直積」から作る

211 件から 1512 件へ増やした。増やし方の原則は「同じ検証の言い換えで
水増ししない」ことで、追加した 1301 件はすべて、入力空間の直積を
参照式・遷移表・期待エラーと 1 件ずつ照合する形にした。代表例は
layout の占有量で、容量 {2,4,8} × (write, read) の全順序対を
「write − read、ただし read > write は None」という定義そのものと
突き合わせる。crc32c は長さ 0..=256 をビット単位の参照実装と
長さごとに照合する。こうしておくと、件数は「網羅した格子の点の数」
として意味を持つ。

歯ごたえは変異スポットチェックで確認した。(1) occupancy の
checked_sub の被減数を入れ替えると layout 行列の非対称な半分が
軒並み落ちた。(2) decode_descriptor の容量判定を `>` から `>=` に
変えると「容量ちょうどの長さは受理」が落ちた。(3) OVERFLOW からの
復帰判定を `<` から `<=` に変えると復帰閾値の境界 3 件が落ちた。
いずれも今回の行列が境界を正確に押さえている証拠で、変異は戻した。

書いている途中で、仕様ではなく現行実装の癖をいくつか固定することに
なった。usage_percent は u64::MAX 付近で飽和して 1% を返す
(比率として意味をなさない領域)、容量超過の Payload はイベントごと
落とすのではなく Descriptor を残して劣化させる、DETACH 後の呼出の
数え上げは handle の世代を見ない、等である。癖を「正しい」と主張は
しない。ただ、無言で変わると気づけないので、テストの形で明示した。

正直な限界も残す。PBT のケース数は据え置いた (件数には効かず、
実行時間だけが伸びるため)。loom のモデル追加も今回はしていない。
そして行列の一部は現行の振る舞いを固定する性格付けテストなので、
今後の修正 (コードレビュー指摘の反映など) で意図的に書き換える
箇所が出るはずで、そのときは「テストを直した理由」をまたここに残す。

### 2026-11-09 — コードレビュー R1〜R7 の修正: P0 は全部「順序」と「信頼境界」だった

外部レビュー (対象は remote main のスナップショット) で P0 が 3 件、
P1 が 4 件出た。全件を現行コードで確認し、回帰テスト先行で直した。
テスト総数は 1512 → 1530 件。個別の項目は traceability の D64〜D73。

一番効いたのは R3 (Slot 回収の競合) の再現方法だった。これまでの
loom は MiniRing という「プロトコルの最小再現」で、実 SlotPool の
原子操作の順序そのものは検査していなかった。だから FREE 公開 →
世代加算という誤った順序が素通りした。今回は host_reclaim と claim の
操作列を 1 ステップずつ loom へ転写したモデルを書き、旧順序では
「回収済みなのに旧世代が見える」実行を loom が即座に見つけた。
実 SlotPool の並行ストレスでも同じ不変条件違反 (同一世代の二重発行)
が出た。抽象モデルと実装転写は役割が違う、という当たり前を、
検出漏れの形で学んだ。修正は RECLAIMABLE → RECLAIMING → FREE の
3 段階にし、世代と所有者は RECLAIMING の間に更新して FREE の
Release 公開を最後にした (行列の st_5 はこの意図的変更で書き換えた)。

R2 は信頼境界の話だった。検証付き経路 (ValidatingHost) は別に存在
したのに、通常の DrainWorker は無検証の RingReader で共有メモリの
長さと位置を信じてコピーしていた。DrainWorker を「像へコピー →
ValidatingReader で検証 → 検証が通った分だけ共有 Cursor を前進」に
作り替え、snapshot の drain_image を通常経路そのものにした。副産物
として、回収再開時に DrainWorker 側の期待 Sequence と像側の実績が
二重管理になっており再開直後に偽の欠落を数える不具合が見つかり、
欠落数え上げは ValidatingReader 側へ一元化した。「同じ事実は
1 か所で数える」は並行コードだけでなく会計にも効く。

R1 (全体 Mutex) は TLS + Ring ごと Mutex + 管理パスの分離で解消した。
回帰テストは「満杯 Ring で BOUNDED_WAIT に入ったスレッドがいる間に
別スレッドの記録が即座に返る」を時間で測る形で、旧実装では上限の
800ms ほぼそのまま待たされて落ちた。R7 (space_available の Ring
ごと化) は、旧 API では「Ring ごとに束ねる」こと自体を表現できず、
再現テストが書けなかった。新しい結線テストで代替し、この限界は
traceability にも明記した。R6 は性格付けテストの申し送りどおり、
dropped の容量拒否ケースを「受理」に書き換えた。元の長さの上限は
u32 の表現最大値と決め、writer 側は切り捨てず飽和させることで
「Descriptor の長さが実長を過小に示す」ことが無いようにした。

正直な残り: MSRV 1.77 でのビルド確認は手元に該当ツールチェーンが
無く CI 待ち。loom の転写モデルは実装の操作列の写しであり、実装
そのものを loom で走らせたわけではない (実物はストレスが担う)。
Windows のプロセス間経路は従来どおり CI 依存で、検証済みは依然 0 件。

### 2026-11-09 — 調整値は「測って維持する」も決定だった

A73 の掃引を `shirusu-tuning-bench` で回した結果、既定値は全部そのまま
になった。Ring 4096 件 / 1MiB、BOUNDED_WAIT 1ms、再確認 2ms、復帰閾値 50%、
Slot 32・低水位 8——どれも「変える理由が測れなかった」。数字を捏ねて
変える方がよほど危ないので、維持を決定として記録した。

測定で面白かったのは S1b の欠落率の仕組みだった。payload 容量が先に
尽きる構成では欠落がほぼ 0%、descriptor と payload が同時に尽きる構成
では欠落率 81%——同じ「遅い Host」でも構成でここまで違う。理由は
BOUNDED_WAIT の振る舞いで、payload だけが尽きている間は書き手が 1ms
待って Host を待つ（attempted 自体が抑えられる）のに対し、descriptor
まで尽きると待つ場所が無くなり高速で欠落させる。欠落率は「どれだけ
書こうとしたか」の分母に支配されるので、構成間の比較は Published 件数
で見るのが正しい、という当たり前を数字で確認した格好だ。

S3 は一度測り直した。最初はデータ到着を 7ms 固定にしていて、5ms と
10ms の区間が同じ再確認境界（10ms）に当たって遅延がほぼ同じになる、
という測り方の罠に自分で引っかかった。到着時刻を 1〜21ms でランダム化
したら、区間の半分に沿う綺麗な序列が出た。ベンチの設計ミスは製品の
バグより先にテストが嘘をつく、という 00:55 の所感の繰り返しだった。

S4 の小刻み回収の話も収穫だった。OVERFLOW 中に 1 件ずつ回収しては
書く、を繰り返しても復帰しない。劣化 Descriptor が空いた枠を即座に
埋め戻すからだ。復帰には「まとまった」回収が要る。これは仕様の
「復帰閾値を下回るまで」という文言の通りなのだが、Host の回収が
1 件ずつしか進まない実装だと復帰が遅れる、という運用上の含意がある。
DrainWorker は drain_all でまとめて回収するので現行経路では問題に
ならないが、回収を小分けにする実装を後で入れるなら気をつける点だ。

正直な残り: 通知閾値（notify_threshold_percent）は掃引していない。
復帰閾値と別物で、通知の発火条件にしか効かないため今回は対象外とした。
Windows 実機の数値は CI 待ち。S1a で 1 ラウンドだけ 449 件 (0.9%)
の欠落が出た外れ値があり、consumer スレッドのスケジューリング遅延
とみているが、断定はしていない（他の全ラウンドは 0 件）。

### 2026-11-09 — 非同期拡張で一番悩んだのは Mapping の「所有権の形」だった

A70 のフロー自体は素直だった。要求フラグを管理スレッドが消費して
Host へ送り、Host が Mapping を作って配送し、管理スレッドが登録する。
二重作成の防止も、ラッチ型フラグ＋進行中 1 件のゲートで自然に閉じた。
進行中に立った要求はフラグが立ったまま残るので、完了後の step で
改めて処理される（捨てないし、重ねて送らない）。

本当に悩んだのは、新しい Mapping のメモリを「誰が持つか」だった。
Windows の本番形では Host と Agent が同じ File Mapping の別々の写像を
持つ（duplicate したハンドルから Agent が自分の写像を作る）。ところが
Linux スタブの SharedMapping はヒープの Vec で所有者が 1 人しかいない。
Host が所有権ごと Agent へ渡してしまうと、Host が回収できなくなる。
結局プロセス内実装の取り決めは「Host が保持し続け、Agent は base を
借りる」にした。Windows 経路では Agent が自分の写像を所有するので、
所有権の形はプラットフォームで非対称になる。プロセス内 E2E はフロー
（要求→作成→配送→登録→記録→回収）を証明するもので、所有権の形まで
証明するものではない、という留保付きだ。Windows プロセス間の往復は
CI の実機 E2E が担う。

あと 2 つ、実装中に確かめられてよかったこと。1 つは追加 Slot の
generation 0。初期 Slot が 1 から始まる慣習に 0 を混ぜるのは最初
違和感があったが、0 は「まだ誰も使っていない」の素直な表現で、検証側は
期待値との等値だけを見るため特別扱いが一切要らなかった。E2E で
generation 0 の一時キーが付いたイベントを回収できたのが確認になった。
もう 1 つは SlotPool の `slot()` が `&Slot` を返していたこと。Vec を
伸ばせる形にするには `Arc<Slot>` にする必要があったが、呼び出し側は
全てメソッド呼び出しだけだったので、返り値の型を変えても呼び出し側の
修正は 0 件で済んだ。生の参照を返す API が「中身へのアクセスだけ」を
要求していたおかげで、コンテナの変更が波及しなかった。

残る気になる点: 破棄した要求の配送が遅れて届く場合。Host 停止を検知
して要求を破棄した後、遅れた配送がチャネルに残ることがある。要求と
配送は 1 対 1 で順序どおりに処理されるため、遅れた配送は次の要求の
分として消費されるだけで取り違えは起きない。ただ、死んだ Host の
Mapping を登録することになるので、記録自体は Host 停止で素通しに
なっている（C10 の設計どおり）。実害は無いが、頭の片隅に置いておく。

### 2026-11-09 — レビュー第2回デルタ: 「時刻の原点」と「モデルの粒度」を直した

第2回レビューの未対応デルタ 3 件（項目5後半・6・8）を片付けた。

Clock の分離（項目8）で一番引っかかったのは、既定の時刻源の原点を
どこに置くかだ。本物の QPC は OS が決める原点を持ち、プロセス間で
比較できる。std だけではそれが取れないので、transport の既定実装は
「プロセス全体で 1 つの OnceLock 原点」にした。インスタンスを
作り直しても原点が動かない、という性質だけは QPC と揃える。
プロセス間比較の本体は transport-win の QpcTimestampSource
（QueryPerformanceCounter の FFI）が担い、Agent は
with_timestamp_source で差し替える。待機実測の Clock と刻印の源を
分けたことで、R7 の「Ring ごとに Clock を差し替える」が時刻系に
干渉しなくなった。matrix_ring の ts_* ケースは「刻印＝待機 Clock」
という旧性格付けだったので、時刻源を差し替える形に書き換えた
（意図した変更への追随として記録しておく）。A30 の「待機時間は
QPC で実測」は待機側の話なので、意味は変えていない。

TLA+（項目6）は、Reclaim を ReclaimBegin（Generation 更新と
フラグクリア）と PublishFree（FREE 公開）に割った。あわせて
Claim が観測した Generation を記録し、「取得済み Slot の
Generation は変わらない」という不変条件 ClaimedGenerationIsCurrent
を足した。主モデルは全 7 条件が成立（990,889 状態）。旧順序の
変種モデルは 924 状態でこの不変条件の違反を検出した。違反を
検出できること自体が「モデルが競合を表現できている」証跡に
なる、というのが今回の肝で、scripts/ci/tla.sh には両方向の
主張（主モデルは通る／変種は違反する）を入れた。

RingReader（項目5後半）は、本番経路が検証付きに統一された後も
残っていた「直接呼ばれたら素通り」の穴を塞いだ。drain の
コピー前に ValidatingReader と同じ最小検証を入れ、破損なら
Cursor を進めず DrainBatch::integrity_error で返す。格下げ
（テスト専用）の看板はそのままで、あくまで多層防御として
足したものだ。検証順序（範囲→連続性）は検証側と揃えたため、
位置をずらした改竄テストは最初「連続性で捕まえる」つもりが
「範囲で捕まった」——テスト側の期待を組み直す一幕があった。
検査順序も契約の一部だと改めて思う。

引き継いだスキャフォールドは各モジュールの質が高かった一方、

### 2026-11-09 — Phase 3（フック＋レコーダ）: 「記録できる」と「記録できたと言える」は別の仕事だった

フック方式は IAT フックを選んだ。初期 API セット（CreateFileW /
ReadFile / WriteFile / CloseHandle）が通常インポートで足りる以上、
インライン フックの命令デコードと巻き戻しの危険を今は買う理由が
ない。副作用として、計画・スキーマ・キャプチャの全部が
プラットフォーム非依存になり、Windows 実機なしで単体テストを
厚くできた。捕捉できない経路（GetProcAddress・DLL 内直接呼び
出し）は「静かに欠ける」のではなく、計画の missing として
Coverage に出す形にした。

セッション実装で時間を食ったのは正常系ではなく境界だった。
未初期化 Ring（ゼロ埋め領域は BadMagic で検証に落ちる）を
「エラー」ではなく「まだ Agent が来ていない保留」として扱う
ために、Worker 生成を Magic 確認後へ遅延させた。対象が途中で
死ぬ・共有メモリが壊れる、は異常系というより通常の終わり方で、
回収済み分を Trace に残し Integrity に正直に刻むのが本体の
仕事だった。破損注入テストで write cursor を壊すと Ring が
停止し、既回収 6 件が残って Event Integrity が Lost になる
ところまで確認した。

正直な限界も 2 つ残した。第一にスロットは 1 回限り： Host から
Agent へ「回収済み」を返すプロセス間チャネルが無く、スレッドが
大量に生滅する対象では枯渇しうる。Agent 内では数えているが
Host からは見えないので、Coverage の注記として総括に残した。
第二に、Windows 実動（実フック・注入・E2E）はこの環境では
1 行も実行できていない。check は両ターゲットで通したが、
「動く」と言うのは CI（windows-x64 ジョブの capture-e2e）が
緑になってからだ。テスト +36 件で総数 1673 件、traceability は
G01〜G14 を追加して 215 項目。

### 2026-11-09 — Phase 4（解析＋差分＋テスト基礎）: 「比べる」と「判定する」をコードの形で分けた

Phase 4 は解析側の 4 クレート（analysis / cli / compare / test）。
検査 CLI は overview の表どおり `shirusu inspect / dump /
export` にし、フィルタは独自クエリ言語を作らず CLI オプションの
組にした。ダンプ出力はゴールデンテストで固定してあるので、
表示形式を変えたら必ず差分として現れる。

差分エンジンで一番大事にしたのは、レビュー第3回 §4 の線引き
――「記録することと正しさを判定することは別」――を、注意書き
ではなく出力形式そのもので守ることだった。出てくるのは
「候補」で、種別と重要度と根拠イベントへの参照だけを持ち、
違反かどうかは言わない。留保文（CANDIDATE_NOTICE）は人間向け
にも JSON にも常時付け、終了コード 1 も「候補あり」であって
「違反確定」ではないと明記した。判定が欲しくなったら
shirusu-test のルールとして人が書く、という役割分担である。

対応づけは overview の指定どおり、呼び出し列の単純照合では
なくオブジェクトを主軸にした。ハンドルは「生成した CallLeave
の return」から相関させ、同一性は (生成 API, 生成序数) で
持つ。おかげで Trace 全体のハンドル再番号付けは PBT でも
候補ゼロになる。逆に一番危ういのは正規化の前提のほうで、
「U64 フィールドはハンドル/ポインタ級」という Schema 規約への
依存は残る。個数を U64 で返すような API が将来入ったら、
生成と誤認しないための例外表が要る。これは H05/H06 に
前提として明記した。

正直な限界も残した。スレッドの対応は出現順の序数であり、
スレッド生成順が環境で変われば非対象呼び出しの整列は崩れる
（オブジェクト操作の比較はスレッドに依存しないので主軸は
保たれる）。親子 call の構造比較は未実装。巨大な操作列では
LCS の DP が上限（4M セル）を超えると貪欲整列に劣化し、
結果が変わりうることも H13 に書いた。テストは +40 件で
総数 1713 件、新規クレートは Windows 両ターゲットの check も
通過。traceability は H01〜H13 を追加して 228 項目。

### 2026-11-09 — Phase 5（ippai 連携基盤）: 「相手が従う契約」を先に固定した

Phase 5 はレビュー第3回が描いた構図――Windows と sake の
両側から同形式の Trace を取り、差分を最小の Probe にして
ippai の回帰テストへ――の、shirusu 側で用意できる半分である。
ippai / sake のコードはこのワークスペースに無い。だから
成果物は「動く統合」ではなく、(1) 外部レコーダ向けの
エミッタキット shirusu-emit、(2) 適合性チェッカ
shirusu-conformance、(3) 差分→Probe バンドル生成
shirusu-probe、(4) ippai 側が従う契約 docs/ippai-integration.md
の 4 点に絞り、境界は文書の冒頭に明記した。統合があるかの
ように書くことが、この Phase では一番やってはいけない嘘になる。

エミッタキットで意識したのは、生の TraceWriter が保証する
「形式の不変条件」と、compare が前提とする「規約」は別物だ
ということ。前方参照禁止やチャンク分割は形式の話だが、
sequence の単調性、Enter/Leave の対応、生成イベントによる
オブジェクト相関、Finalization の存在は、書き手が自前で
守らないと静かに崩れる。崩れても Trace としては読めてしまう
のが厄介で、だからキットは採番と対応づけを肩代わりし、
適合性チェッカは 10 項目で外から点検できるようにした。
共有 API セットの同一性は content_hash で決まるので、
「同じ API を記録している」はハッシュ一致という機械的な
事実に帰着する。本体のフック表との照合テストも入れたので、
定義が drift したらテストが落ちる。

ルール生成は「推測でルールを書かない」を徹底した。種別ごとに
戦略を用意し、両 Trace で実際に評価して「左 pass・右 fail」が
成立したものだけを採用する。おかげで、v1 ルール形式では
表現できない候補（Payload の内容差分など）は「ルール化
できない」と正直に落ちる。落ちた理由（試した戦略と棄却理由）
は manifest に残るので、ルール形式 v2 を検討するときの
材料になる。途中で面白い発見もあった：shirusu-test の JSON
パーサは正の整数を U64 に正規化するため、生成した仕様の
「往復」は構造一致では測れず、「読み戻しても識別が成立する」
こと自体を不変条件にする必要があった。

トリミングは再解釈ではなく抜き出しに徹した。sequence・
引数・Blob ID は元のまま、完全性 3 指標も元の申告を引き継ぎ、
「セッション全体の記録ではない」ことを Trace 内の notes と
ブリーフの両方に残す。テストは +28 件で総数 1741 件。
残りは全部 ippai 側：sake 側エミッタの実装、記録ペアの運用、
バンドルの取り込み、そして候補が本当に違反かの判定である。

### 2026-11-09 — 転送層の残項目: 「未着手」は 5 種類の違う仕事だった

チェックリストに残った未着手 8 件（A74・A75・D53〜D56・D77。D41 は
CI ループそのもの）を片付けた。並べてみると、同じ「未着手」でも
中身が全部違う。測定（A74）、検討（A75）、証跡の仕組み化（D53）、
独立性の実証（D56）、プロセス間 E2E の組み合わせ（D77）、そして
CI の配線だけのもの（D54・D55）。分けて考えるまでが仕事だった。

A74 は測定器（shirusu-atomic-bench）を作り、切替判断の基準を
先に文章で固定した。手元では x86_64 の参考値しか取れず
（i686 は 32bit ローダが無く実行自体が不能）、本命の WoW64 実測は
CI に置いた。「測れないものは測れない」と書くのが測定の一部だと
改めて思う。A75 は書かない決定の記録である。分割コピーのコストは
コピー回数だけで総量は同じ、という見積もりが立つと、二重マッピングは
「速くする案」ではなく「互換性を切り替える案」だと分かる。
結論は条件付き保留で、再検討の条件を 3 つ固定した。

D53 は「失敗したときに何が残るか」を仕組みにした。proptest の
regressions が Seed と縮小を担い、DST は証跡 JSON（リビジョン・
構成・操作列・注入故障）を持ち、決定的再実行器で再生できる。
loom の失敗スケジュールは保存できないので、旧順序モデルが
落ちること自体を should_panic で固定した。「回帰テストに加える」
は、失敗の種類ごとに形が違う。

D56 は独立性の「宣言」を「実証」に変えた。監査では、参照モデルが
期待値計算に validate を使っていないことと、唯一残っていた
usage_percent の流用を切り離した。実証は mutation で、占有量計算と
Generation 加算を壊したコピーで参照モデル側のテストが実際に
落ちることを確認した。モデルが実装に追随していたら落ちない、
というのがこの確認の肝である。

D77 は既存 E2E との突き合わせから始めた。capture-e2e は Hook と
Trace の経路、cross_arch は生 RingWriter とポーリングで、どちらも
「実 Agent → Event 待機 → 検証付き Host → Slot 再利用」の
組み合わせではなかった。新シナリオ production_path_interprocess は、
producer が DLL と同じ手順で Agent を組み、Host が
wait_with_recheck で待ち、DrainWorker で検証しながら回収し、
DETACH 確認の後にだけ再利用を許可する。Windows 実走は CI 待ち。

テストは +8 件で総数 1749 件（failure_evidence 7 + loom 旧順序 1）。
未着手は D41（CI フィードバックループ）のみになった。

### 2026-11-09 — レビュー第4回: 「緑」だったジョブが空だった

今回いちばん重い指摘はコードのバグではなく、run #4 の
windows-x64 が「成功」と表示されながら中身で 3 件失敗していた
ことだった。PowerShell の `$ErrorActionPreference = "Stop"` は
ネイティブコマンドの終了コードを見ない。成功したコマンドが
後から走ると、失敗したコマンドの `$LASTEXITCODE` は上書きされ、
ジョブは緑のまま終わる。直し方は全ネイティブコマンドを
`Invoke-Native` ヘルパー経由にすることだが、それだけでは
「直ったこと」自体が次の CI で検証できない。そこで意図的に
失敗するコマンドを踏ませるカナリア (canary-exit-code.ps1) を
両 Windows スクリプトの先頭に入れた。今後は終了コード伝播が
壊れたら、どのジョブも最初のステップで落ちる。検証の仕組みは
検証対象と同じ経路で常に試されるべき、というのが今回の教訓。
なお PowerShell はこの VM に無いため、スクリプトの実挙動は
CI 待ちである（ここで「直った」とは言わない）。

x86 の `(len >> 32)` は、check では発火しない
deny(arithmetic_overflow) が build でのみ牙を剥く実例だった。
「Windows ターゲットの確認は build で」という運用は前回までの
経験則だったが、今回はそれが無ければ wow64 の赤の原因を
ビルドエラーではなく実行時エラーとして追い続けるところだった。

正規化の #7 は設計の置き場の話だった。U64 がハンドルなのか
ただの数なのかは、値からは決して分からない。型 (Ty) から
推測するのをやめ、答えは Schema の側に置いた (FieldDef.flags の
bit2..=4 に ValueKind)。フック表とエミッタの共有 API セットは
content_hash のピンで結ばれているため、意味種別の追加は両者を
同時に変える必要があり、ピンがその同期を機械的に保証した。
推測で動いていた旧 Schema には従来規約へのフォールバックを
残し、限界はモジュールの文書に明記した。

#8 は「対象が 0 件」をエラーとして扱う設計の誤りだった。
ファイル API を使わないアプリは普通に存在する。殺すべきなのは
プロセスではなく情報の欠落で、欠落は Coverage に記録するのが
正しい置き場だった。#9 は逆に「付けっぱなし」の問題で、
IAT フックの解除には順序（記録の無効化 → 進行中呼び出しの

HookRuntime に置いたことで、この順序は Windows 実走に頼らず
Linux の単体テストで固定できた。recorder_launch 側の呼び出し

管理スレッドの割り込み順序と、容量と取得可能性の分離が原因で、

テストは +24 件で総数 1773 件。traceability に J01〜J11 を

### 2026-11-09 18:29 — テストの「待ち方」が間違っていると、仕組みが正しくても落ちる

定時実行で expansion_e2e の負荷時 1 回の失敗を掘り返した。レビュー第4回
の時点では「100ms の待ち時間の仮定」と記録していたが、再現してみると
原因は 2 件とも別の場所にあった。

1 件目は host_stop テスト。管理スレッドを claim の前に起動すると、
claim 2 で立った要求フラグを管理スレッドが claim 3 の前に消費し、
claim 3 がフラグを再び立てる（slot.rs の再ラッチは仕様どおりで、
agent 側の単体テスト `duplicate_requests_suppressed_while_in_flight`
がその挙動を文書化している）。破棄後に 2 件目の要求が送られて
`requested` が 2 になり、`requested == 1` の断言が落ちる。claim 間に
10ms を挟むと `requested: 2, discarded_host_stopped: 2` で赤になる
ことを確認してから、管理スレッドの起動を 3 本の claim の後へ移し、
要求をちょうど 1 件に決めた。仕組みは正しく、テストの起動順序だけが
非決定的だった。

2 件目は往復テスト。J06 の PREPARING 導入後、追加 Slot は add 時点で
容量に数えられるが取得不能で、publish で初めて FREE になる。
待機が容量（`pool.capacity()`）を見ていたため、add と publish の間の
窓で待機が抜けて `thread_begin(4)` が None を返した。30 回ループの
5 回目で再現した。待つべきは容量ではなく取得可能性
（`free_count() > 0`）だった。直後は 30 回連続で全通過。

教訓は 2 つ。テストが待つ条件は「テストが本当に知りたい状態」と
一致させなければならず、容量は「Slot がある」ことしか言わない。
そして「負荷時に 1 度だけ落ちた」は放置してよい観測ではなく、
窓を広げて再現すれば原因は読める。待ち時間の仮定が残るのは破棄の
検知（100ms はポーリング 5ms の 20 回分）だけで、これは従来の
タイミングテストと同程度の余裕として残している。

### 2026-11-09 19:29 — MSRV 三択の検証を `--tests` まで回した：決める材料は揃った

定時実行で、17:44 時点で「代替案」とだけ記録されていた MSRV 1.85 /

workspace の `rust-version` を更新し、下のピン一式を Cargo.lock に

1.9.0=1.82、1.10.0=1.84、1.11.0=1.85 と確認した）。なお
/tmp は 512M の tmpfs で、スクラッチの target 3 個分で満杯になり

以後スクラッチは home 側のディスクに置く。

### 2026-11-11 05:29 — L12: repair は「捨てる判断の列挙」だった

前回候補に挙げた L12（`shirusu repair` CLI）を実施した。ライブラリ側の回復意味論（F11）は既にあり、残っていたのは CLI としての配線と報告だった。実装してみると、repair の本質は「何を残すか」より「何を捨てて、どう数えるか」だった。捨てる判断は 3 種に集約される。参照先 Blob が無いイベント（MissingBlob。内容を推測して補わない）、Header と session_id が異なる Batch（SessionMismatch。書き換えて取り込まない）、同一スレッドで sequence が退行する Batch（Writer の不変条件に反するため、並べ替えて取り込まない）。いずれも「推測で作らない」という overview の一行の具体化で、捨てた分は原因別に数えて報告に残す。修復の出力が「読めたものだけ」であることは、報告の lost_events を見れば検証できる。

Writer の不変条件は CLI 側で事前に鏡写しした。sequence の退行検査を validate_batch と同じ規則で先に行い、write_batch の失敗を「起きないはずの防御」にした。ただし完全ではない。add_payload（Blob の追加）が write_batch より先に走るため、万一 write_batch が失敗した場合、追加済みの Blob が未参照のまま出力に残る。事前検査で実質到達しない経路だが、Blob の追加と Batch の書き込みが別操作である以上、原理的には残る。次にこの辺りを触るなら、Blob の追加を Batch の成否に紐付ける設計を検討する。

テストでは、TraceWriter では書けない入力をブロック単位で合成した。EventChunk を Finalization の後に追記し、session_id の不一致と sequence の退行を作る。Reader は Finalization の後でも走査を続けるため、この合成が通る。回復意味論の「走査は Block 列を順に読むだけ」という性質を、テストがそのまま利用している形だ。

編集ミスを一つした。usage() に repair 行を追加するとき、文字列リテラルの途中に閉じ引用符を入れてしまい、後続の行が文字列の外に出た。コンパイラが即座に 30 件以上のエラーを出したのですぐ気付けたが、`\n\` で継続する長い文字列リテラルへの行追加は、閉じ位置の確認を一呼吸置いてやる必要がある。

### 2026-11-11 06:29 — L11: `reserved` の転用は A72 の修正であって破棄ではない

### 2026-11-11 08:29 — A77: 欠落は「数える」のであって「無いことにする」のではない

前回候補に挙げた A77（Windows プロセス間メモリ順序ストレステスト）を実施した。producer（別プロセス）が実 Agent で 100 万件を順に書き、supervisor（x64 Host）が検証付き DrainWorker で回収する。D77 が 2,200 件・2 フェーズで Slot 再利用を確かめるものなら、A77 は「プロセスを越えて公開順が保たれるか」を高負荷で確かめるものだ。spec の不変条件節が「単一プロセス内のユニットテストでは確かめられない」と書くのは、この一点のためだ。

検証ロジックは `verify_memory_order_stress` としてプラットフォーム非依存の純粋関数に切り出した。判定は 5 つの保存則だ。順序・内容（payload が 0..N を順にちょうど 1 回ずつ）、payload_keys が N 件、integrity_lost が立っていないこと、欠落会計（SequenceGap の合計 == 書き手が報告した dropped_events）、劣化会計（回収した descriptor 総数 == N + degraded_events）。この切り出しの狙いは、Windows 実走部（supervisor の起動・待機・回収）は CI でしか動かせないが、判定そのものは Linux で 10 件の合成ストリームで先に縛れることだ。判定がプラットフォーム非依存なら、実走の失敗を「判定のバグか、実走の問題か」に切り分けられる。

欠落会計の鍵は、Dropped と PublishedDegraded の違いだ。Dropped は sequence を払って欠番を作る（descriptor は残らない）。producer は同じ call_id を書き直すので、欠番は必ず dropped と 1 対 1 で対応する。だから gaps == dropped が成り立たなければ、それは説明のつかない欠落だ。逆に PublishedDegraded は descriptor を残すので、回収総数に現れる。total == N + degraded が成り立たなければ、descriptor の数え落としだ。「欠落が無いこと」を主張するのではなく、「欠落があれば必ず会計に現れる」ことを主張する形にした。D51 のソークが同じ保存則を単一プロセスで確かめているのと対になる。

二つ、実装中の罠があった。第一に、`cargo test` は `./target/debug/` の通常バイナリを更新しない。`--list` の確認で新シナリオが出てこず、`--memory-order-stress` が無視されて `--all` が走った。ビルド成果物の確認には `cargo build` が要る。第二に、Windows 専用関数 `agent_from_mapping` の戻り値に `Arc<SlotPool>` と書いたら、関数内の `use` はシグネチャに効かず E0425 になった。Linux ビルドではその関数はコンパイル対象外のため、この誤りは Windows の check でしか見えない。F21・L11 のときと同じ「Windows 専用コードの誤りは Linux では見えない」という話の三度目で、対策も同じく `cargo check --target` を回すことだ。今回は x64 の `--workspace --all-targets` と i686 の e2e `--all-targets` を通した。

### 2026-11-11 11:29 — L07: 分類は「判定基準の優先順位」であって「名前の一致」ではない

前回候補に挙げた L07（モジュール分類）を実施した。分類器の核心は、4 分類の「判定基準」を優先順位付きの規則に落とすことだった。難しいのは Windows と Runtime の境界で、msvcp140.dll や ucrtbase.dll は System32 にあり Microsoft 署名付きなので、表の Windows 基準（配置＋署名）だけを読めば Windows になる。しかし overview は「`fopen` 経由の `CreateFileW` も記録される」と書いており、`fopen` は ucrtbase / msvcp の関数だ。Runtime から Windows API への呼び出しを記録するのが標準の境界なら、これらは Runtime でなければならない。だから既知の実行基盤の判定を Windows 判定より先に置いた。表の「名前ではなく判定基準で分類」という一行は、「名前で分類するな」という意味ではなく、「分類はモジュールが何者か（実行基盤か、OS の一部か）で決め、ファイル名はその識別の手がかりに過ぎない」という意味だと読んだ。実行基盤の一覧はその識別規則として module.rs のコメントに明記した。

API Set の扱いも、契約名と実装モジュールの「両方を記録する」が肝だった。契約名だけでは「何が実行されたか」が分からず、実装モジュールだけでは「呼び出し側が何を要求したか」が分からない。`ModuleClassification` は両方を持ち、解決できなかった場合は Unknown として不確実フラグを立てる。解決の連鎖は深さ 2 までで打ち切り、自己参照の契約名が無限ループにならないようにした。

CLI の上書きは「当たらなければ残す」にした。capture 開始時に分かるモジュールは起動対象の exe だけで、`--module-class kernel32.dll=windows` のような上書きは、その時点では必ず「当たらない」。当たらなかった上書きを捨てれば、利用者の指定は黙って消える。だから未一致の上書きは上書きエントリとして Trace に残し、後から現れるモジュールに適用できるようにした。「指定したのに効かない」は、黙って消えるより、Trace に残って後から分かる方がましだ。

副次として、`CaptureEnvironment` にフィールドを足すと、リテラル構築が 5 か所、関連して `CaptureSessionConfig` が 3 か所で壊れた。いずれも `..Default::default()` を付けていない全フィールド列挙のリテラルだ。フィールド追加のたびに壊れるリテラルは、構造体にフィールドを足すコストそのものだ。今回も全部直したが、リテラルを全列挙するテストヘルパーが多いほど、このコストは増える。次に構造体へフィールドを足すときは、テストヘルパーを `..Default::default()` に寄せるか、コンストラクタに寄せるかを先に決める。

### 2026-11-11 12:29 — L09: 「記録しない」は「捨てる」ではなく「集計する」か「選ぶ」かだ

前回候補に挙げた L09（記録モード profile / filtered）を実施した。設計の核心は、3 モードを「保存するイベントの集合の違い」ではなく「保存の仕方の違い」として分けることだった。`full` は全保存、`filtered` は選んで保存、`profile` は保存せずに集計する。3 つを同じ `record_batch` の入口で振り分けるのは、モードが Host の変換層の性質であって、Agent や転送層の性質ではないからだ。Agent はどのモードでも全イベントを Ring へ書く。Agent 側で間引けば Ring の圧迫は減るが、間引きの判断を Agent に持たせると「Agent が何を落としたか」が Host から見えなくなる。落とす判断は Host の一か所に集め、Agent は「全部送る」に徹する方が、欠落の会計（Loss Record と Finalization の三指標）が一貫する。

`profile` の集計で難しかったのは、enter / leave の対応付けの鍵だった。DrainWorker の `track_call` が既に (call_id) で対応付けているが、あれはスレッド単位の Worker の中で閉じている。Recorder は複数スレッドの Batch を順に受けるため、鍵は (thread, call_id) にした。対応の無い enter / leave は「欠落」ではなく「未対応」として calls に数えず、enters / leaves だけに数える。未対応を欠落（Loss）として扱わなかったのは、記録の終わり方（対象がまだ動いている・leave が次の Batch にある）では未対応は正常だからだ。`calls` は「揃ったものだけ」という厳密な定義にし、`enters` / `leaves` との差が未対応の量を表すようにした。

`filtered` の落としどころも、Blob 化の前にした。Payload を Blob にしてから落とすと、不要な Blob がファイルに残る。`record_batch` の入口で落とすと、sequence の欠番だけが残る。Writer の不変条件は退行の拒否だけで欠番は許容されるため、欠番は Loss として扱わない。欠番と Loss Record は別物だ、という区別がここでも要った。

副次として、構造体にフィールドを足すたびに壊れるリテラルの問題がまた出た。今回は `ReadTrace` が 2 か所（probe・conformance）、`CaptureSessionConfig` が 3 か所（host テスト 2 件・e2e）で壊れた。e2e の漏れは Linux のテストでは見えず、Windows の check で見つかった。F21 のときとまったく同じ見逃しパターンで、Windows 専用コードは Linux の `cargo test --workspace` では検証されない。Windows の check を毎回回す運用が、ここでも効いた。

### 2026-11-11 13:29 — L08: 例外は「捕捉しない」ことで透過する

前回候補に挙げた L08（例外の透過と CallAborted）を実施した。設計の核心は、例外を「捕まえて記録する」のではなく「捕まえずに、通り過ぎるのを見届ける」ことだった。Detour が例外を catch すれば、例外の型・ペイロード・巻き戻しの経路のどれかで対象アプリの挙動を変えてしまう危険がある。代わりに enter の直後に RAII ガードを立て、正常に戻ったら武装解除し、例外で巻き戻されたときだけ Drop で CallAborted を記録する。ガードは例外を見ないし触らない。例外の伝播は Detour が無い場合と同一で、記録だけが残る。

この設計が成り立つのは、Windows では Rust のフレームも SEH アンワインド情報を持つからだ。外来の C++ 例外や SEH 例外が Detour フレームを巻き戻すとき、Rust の Drop は走る。仮に走らなかった場合でも、失敗モードは「中断の記録漏れ」だけで、例外の伝播は変わらない。漏れた分は Host が「終了不明」（UnknownTermination）として別途扱うので、記録の欠落が無言で消えることはない。Drop 中の記録自体も catch_unwind で包んだ。巻き戻し中の Drop でパニックするとプロセスが abort するため、記録の失敗が例外の伝播を壊す経路は塞いでおく必要があった。

波及の面では、Phase に Aborted を足したことで、コンパイラが「相を網羅で扱っている場所」を全部教えてくれた。view の api_stats と compare の正規化だ。compare では中断を Leave と同じ「呼び出しを閉じるもの」として扱いつつ、NormCall には aborted として別に持たせた。中断と正常終了を同じ leave に畳むと、両者の違いが差分に出なくなるからだ。ただしオブジェクト生成 API では、中断すると生成物が無いため整列で対にならず、MissingCall と ObjectStateDifference として出る。初版のテストはここを CallShapeDifference と期待して失敗した。エンジンの整列が「オブジェクトへの関与」で対応づけを決めている以上、中断した生成呼び出しは対にならないのが正しい振る舞いだ。テストの期待値を直す判断は、エンジンの設計を読み直してから行った。

### 2026-11-11 14:29 — F27: 完了は「新しい種別のイベント」であって「leave の書き換え」ではない

前回候補に挙げた F27（非同期 I/O の完了時取得）を実施した。非同期の ReadFile / WriteFile は leave 時点ではまだ完了しておらず、バッファの中身も転送バイト数も決まっていない。leave に「後で埋める」欄を作る手もあったが、leave は元の API が戻った時点のスナップショットであるべきで、完了時の値を後から書き換えると、leave の意味が「戻り時点」と「完了時点」の二重になってしまう。代わりに転送に `CallCompleted`（kind 8）という新しい種別を足し、完了を観測した時点で、元の API の leave Schema の値列をそのまま載せたイベントを別に記録する。leave は「保留のまま」を正直に残し、完了が「実値」を別イベントで補う。compare は実効 leave として完了の値を優先するので、非同期の完了と同期の leave は値が同じなら一致する。

完了の観測先は、完了を「知らせる」API だけに絞った。GetOverlappedResult と GetQueuedCompletionStatus である。WaitForSingleObject で hEvent を待つ経路や、GetOverlappedResultEx、APC の完了ルーチン経由は対象外として明記した。完了の観測には「いつ、どの操作が、どの値で完了したか」の対応づけが要るが、待機 API は完了を通知しないため、観測のしようがないからだ。対象を広げるなら、まず「完了の通知を受け取る仕組み」そのものを設計し直す必要がある。

登録表の鍵は OVERLAPPED 構造体のアドレスにした。完了は別のスレッド（IOCP の取り出し側）で観測されうるため、表はセッション全体で共有し、スレッドローカルには置かない。Win32 では 1 つの OVERLAPPED を完了前に再利用してはいけないので、同じアドレスでの再登録は上書きでよい。転送バイト数は lpNumberOfBytesTransferred が NULL なら OVERLAPPED.InternalHigh（オフセット 8）から読む。読めなければ完了は記録しない。「分からない値を推測で埋める」より「記録しない」ほうが、Trace の正直さを保てる。

実施後の全体テストで、kind 8 を未知とする前提のテスト 5 件が失敗した。roundtrip の Schema 数と transport の境界テスト 3 系統である。kind の追加は「新しい値を足す」だけでは済まず、「未知の境界をどこに置くか」を決め直す作業でもある。今回は 8 を有効、9 を未知とした。境界テストは「今の境界」を固定するピンであって、境界が動いたらピンも動かすのが正しい。ただし、テストの期待値を動かすときは、動かす理由が「仕様の変更」であることを確認する。今回の 5 件はすべて「kind 8 が有効になった」という仕様変更の直接の帰結で、期待値の安易な緩和ではない。

### 2026-11-11 16:29 — L05: 子は「別 Trace」に分け、来歴は pid で辿る

前回候補に挙げた L05（子プロセス追跡）を実施した。設計の判断は、子をルートと同じ Trace に混ぜないことだった。Trace のイベントは現行 1 プロセス 1 Trace の前提で書かれており、複数プロセスを 1 ファイルに混ぜると、スレッド ID・sequence・session_id のどれも「どのプロセスのものか」を区別できなくなる。代わりに子は `<stem>.child-<pid><ext>` の別ファイルに記録し、子の session_id はルートのものに pid を足して派生させた。来歴はファイル名の pid と、子の Environment の capture_config（`child process pid=<pid> of root pid=<root>`）で辿れる。session_id の派生が wrapping_add である以上、理論上は衝突しうるが、pid が小さい現実の範囲では衝突しない。衝突がありうる設計にしておいて「現実には起きない」で済ませるのは気になるが、session_id 自体が起動時刻のナノ秒という衝突しうる値の上に成り立っているため、同じ強さの前提に載せた。

子孫の判定は ppid の連鎖を辿る。ここで既知の pid を中間のリンクとして使ったのは、親が既に終了してスナップショットに無くても孫を見つけるためだ。Windows では親が死んでも子の ppid は元の親 pid のまま残るので、既知の pid をリンクに使うのは正しい。逆に、スナップショットに無い pid へのリンクは辿れない。親が一度も発見されなかった子の孫は見つからないが、その親は次のスナップショットで発見されるか、既に知っているかのどちらかなので、実運用では稀なはずだ。pid の再利用については保守側に倒した。一度知った pid は二度と返さないため、別ツリーのプロセスが同じ pid を再利用しても誤って注入しない。代わりに、取りこぼしの可能性は残る。完璧な判定には pid と開始時刻の組が必要だが、Toolhelp の PROCESSENTRY32 には開始時刻が無い。将来、開始時刻を取るなら NtQuerySystemInformation への依存が要る。

### 2026-11-11 17:29 — L06: ABI 適合性の正解は「Hook なしの実行」そのものだ

前回候補に挙げた L06（全 Hook 共通の ABI 適合性テスト）を実施した。設計の判断は、Probe に期待値をハードコードしないことだった。浮動小数点の合計が何になるか、構造体の各欄が何になるかは、Probe 自身は知らない。知っているのは「Hook なしで実行したときの値」だけだ。正解を別に持つと、Probe と正解の両方を保守することになり、どちらかがずれたときに「Probe が間違っているのか、Hook が壊したのか」が分からなくなる。Hook なしの実行を正解にすれば、比較が壊れたら Hook が何かを変えた、という一つの結論だけになる。比較器は `ABI_PROBE` 行だけを見て、名前・順序・値を位置ごとに比べる。Probe 行以外の stdout（TARGET_* 行など）は無視する。順序まで比べるのは、Probe の実行順が変わること自体が、フックによる実行経路の変化を示すからだ。

Hook あり実行の成否は `ABI_PROBE_DONE ok` 行で見ている。`LaunchedCapture` が対象の終了コードを返さないためだ。対象がクラッシュしても、TARGET_FAIL で非 0 終了しても、DONE 行は欠けるので比較は失敗する。終了コードを取る API を足す手もあったが、L06 の範囲を超える。DONE 行は「最後まで走り切った」という事実だけを保証し、「結果が正しい」は比較器が保証する、という分担にした。

境界として、SEH 例外が Detour の実行中に起きる経路は扱わなかった。現行 4 API の呼び出しでは SEH を起こす引数が作れない。不正なバッファはカーネルがエラーで返すので、ユーザーモードには例外として届かない。例外 Probe は Rust のパニックの伝播と、巻き戻し後のフック健全性（後続のファイル操作が正常なこと）を対象とした。Detour の途中で例外が起きたときの CallAborted の実動は、L08 の CallGuard の単体テストの範囲に留まる。SEH を起こせる API（たとえばコールバックを呼ぶ API）がフック対象に増えたら、そのときに Probe を足す。

実装中の Rust の落とし穴が二つあった。一つは `unsafe { WriteFile(...) } != 0` が構文エラーになること。ブロック式の直後に二項演算子は置けない。変数に束縛してから比べる。二つは `Path` が DST でワイドポインタのため、`&Path` を `*mut c_void` にキャストできないこと。スレッドプロシージャへ渡すポインタは `&PathBuf`（シン・ポインタ）にした。どちらもコンパイラが教えてくれるので実害は小さいが、FFI の境界では「ポインタの幅」を意識する癖が要る。

### 2026-11-11 18:29 — L10: 性能の倍率は「測るもの」を間違えると嘘になる

前回候補に挙げた L10（性能目標と測定）を実施した。倍率は 1.004x（gui-mix）と 0.987x（high-load）で、どちらも上限（3 倍・5 倍）を大きく下回った。だがこの数字に至るまでに、測定器の側の欠陥を三つ直している。どれも「測れているつもり」の測定だった。

一つ目は Ring の大きさだ。初回は欠落を避けて 64MiB の Payload Ring で測り、gui-mix が 1.300x になった。原因は `DrainWorker::drain_all` が毎回リージョン全体像をコピーすることだ。64MiB の像を 200µs ごとに写す消費者が、producer の CPU を食っていた。実運用の Ring は 4096 件 / 1MiB で像は約 1.3MB だから、本番サイズで測り直すと 1.004x になった。Host の drain コストは Ring サイズに比例する、という設計上の事実を、測定条件がそのまま数値にしていた。

二つ目は `record_batch` の粒度だ。drain のたびに渡すと EventChunk が細切れになり、Trace は 10.4 B/event になった。5,000 件ずつ溜めて渡すと 5.0 B/event になる。ファイルサイズの測定値は、形式の性質ではなく呼び出し側のバッチングを測っていた。F25/F26 が 10,000 件ずつで測っていたのは、このためだったのだと後から分かった。

三つ目は消費者スレッドの終了条件だ。drain→done 確認の順だと、drain の直後に公開された最後の 1 件を落とすレースがあり、20,000 件中 1 件の取りこぼしで発覚した。done 確認を先に行い、最終 drain で全公開を見る順序に直した。1 件の欠落は「誤差」ではなく、終了条件の設計ミスだった。

### 2026-11-11 23:29 — L03: Metadata は「型」をくれるが「意味」はくれない

L03 で一番危なかったのは、動いて見えたところだった。`include!` を配列要素に置いたら「単一式でなければならない」と怒られ、手書き表と生成表を別 const にして `api_table()` で連結する形に落ち着いた。const でスライス連結ができない制約が、かえって表の出自を明示する設計になったのは幸いだった。

本当に危なかったのは x86 の 2 スロット問題だ。汎用 Detour は「引数 1 個 = usize 1 個」で中継するが、x86 では固定 64bit 型がスタック 2 スロットを占める。`SetFilePointerEx` の `LARGE_INTEGER` はメタデータ上ではただの I64 で、見た目は何も問題がない。引数の並びが 1 スロットずつずれ、全ての引数が壊れる。x64 だけ見ていたら気づかない。生成器に 1 スロット制約を入れたのは、ABI の罠を「生成時に弾く」ためのもので、テストが通ったから安全なのではない。`GetTickCount64` の U64 戻りも同じ理由で弾いた。WoW64 の CI で初めて発覚する類の不具合は、生成時に潰すのが一番安い。

設定の罠もあった。`apis.toml` は `[[api]]` と書いたのに serde は `apis` を見ていたため、設定は 0 件として読まれ、生成器は 0 件を黙って生成して終了 0 で終わった。空の入力を成功として通すのは、嘘をつくテストと同じ類の罠だ。`rename` を付け、0 件はエラーにした。

Metadata からは「意味」が取れない、というのも今回の教訓だ。`WIN32_ERROR` を返す API は戻り値自体がエラーコードであり、`GetLastError` は意味がない。だが `WAIT_FAILED` を返す `WaitForSingleObject` の失敗条件は、enum の名前からしか分からない。型だけでは失敗条件は決まらないので、既定は `Never`（常に Stale）に倒し、分かるものだけ設定で上書きする。分からないものを `Unspecified`（生値を意味ありとして扱う）にすると、成功時の残留値をエラーとして記録してしまう。F20 の原則どおり、「分からない」は Stale 側に倒す。

分母は 311 のまま、未着手は 9→8 になった。検証済みは 245 のまま。CI 検証は run #8 待ち。生成 API は 72 件（api_id 7〜78）。レジストリは `--verify-apps` で 12 イベント以上を検査するようになった。

### 2026-11-12 00:29 — L01: BlockEncoder の「配置先 RIP」は引数で渡すものだった

L01 で一番の罠は、iced-x86 の `InstructionBlock::new` の第 2 引数だった。これは元の RIP ではなく**配置先の RIP**で、元の RIP を渡すと命令はその場に「再配置」され、変位は一切直らない。テストが教えてくれた。`call +0` の再配置後も `near_branch_target` がトランポリン＋5 のままだったのを見て、初めて引数の意味を読み違えていたと気づいた。ドキュメントの例は `orig_rip + 8` を渡している。API の引数名が `rip` 一つで、どちらか分からないのはライブラリ側の不親切さだが、読まなかったのはこちらだ。再配置の正しさは「デコードして飛び先を比べる」テストでしか確かめられない。命令をコピーしただけでは、見た目は正しくても意味が違う。

RIP 相対も同じ類の罠だった。`memory_displacement64()` は RIP 相対では生の変位ではなく**絶対アドレス**を返す。テストの計算が合わなかったのは、実装ではなく検証側の前提が違ったからだ。`ip_rel_memory_address()` が正しい比較相手である。iced-x86 の getter は「何を返すか」を doc に書いてある。読むべき場所は、使い方ではなく返り値の意味だった。

`loop` の扱いも、調べる前は「rel8 しかないから拒否」と思い込んでいた。実際には BlockEncoder が `loop short skip; jmp rel32 target` へ書き換えて遠方化する。思い込みで拒否条件を増やすのは、捕捉できるはずの API を Coverage 欠落に回すのと同じだ。分からないものは実装を疑う前に、ライブラリの振る舞いをテストで確かめる。

設置側の安全は、スレッド停止と命令ポインタ検査の二段にした。パッチ中に他スレッドが対象関数の先頭で止まっていたら、その API は見送る。止めること自体が失敗したら全体を見送る。失敗を「設置できなかった API」として数えるのは、IAT の missing と同じ思想だ。解除側も対称で、トランポリン内にスレッドがいれば解放しない。リークするが、実行中のスレッドが解放済み領域へ戻るよりはましだ。

### 2026-11-12 01:29 — L02: COM の「同一性」は、ポインタではなく QueryInterface の結果で決まる

L02 で一番悩んだのは、COM オブジェクトの「同一性」を何で決めるかだった。ポインタは同一性の証拠にならない。同じオブジェクトが `QueryInterface` で別 IID を要求されれば、別ポインタを返すのが COM の仕様だ。だから同一性の正規キーは「`QueryInterface(IID_IUnknown)` が返したポインタ」にした。アプリが実際にその QI を実行したときだけ、別ポインタ同士を同じオブジェクトとして結びつける。標準ではこちらから QI を呼ばない。呼べば参照カウントが動き、アプリの寿命観測が変わるからだ。診断用オプション `--diagnostic-query-interface` は、その副作用を明示したうえで、必要なときだけ有効にする。

方式は「オブジェクト単位の vtable 複製」にした。共有 vtable を書き換えると同じクラスの別オブジェクトまで波及するし、Proxy を挟むとポインタ同一性が壊れる。複製はオブジェクトの vtable ポインタだけを向け替え、複製のスロットを Detour へ向ける。複製 vtable と登録を解放しないのは、Release 後も他スレッドが呼び出し中かもしれないからだ。リークに見えるが、プロセス終了時に OS が回収する。Detour は (vtable インデックス, arity) の組ごとに 1 個だけ作り、全インターフェイスで共有する。Detour は `this` から追跡表を引いてインターフェイス名とメソッド名を復元する。元のメソッドは複製 vtable のアドレスを鍵に引く。24 組の Detour で IUnknown・IShellLinkW・IPersistFile の全メソッドを覆える。

COM メソッドイベントは Win32 API の表とは別枠にした（api_id=1000、enter Schema=10001、leave Schema=10002）。引数は this を除く生スロット値列（上限 4 スロット、L1）で、型付き取得は将来の仕事だ。Factory は `CoCreateInstance` / `CoGetClassObject` を Inline Hook で設置し、Bootstrap は v6 になった（com_options bit0、サイズ 592→600）。

実装中に clippy が教えてくれた罠が二つある。fn item の直接 `as usize` キャストは `function_casts_as_integer` 警告になる。関数ポインタ型を経由してキャストするのが正しい書き方だ。もう一つは `Guid` の inherent `to_string` が `Display` を隠す `inherent_to_string_shadow_display` で、書式は Display 実装に移した。どちらも Linux では通って Windows check で初めて出る類ではないが、clippy の `-D warnings` が無ければ見逃していた。

制限は二つ、仕様に明記した。アタッチ前に存在したオブジェクトは発見できない。同じ実装の別オブジェクトを並べて vtable ポインタの不変を直接確認する E2E はまだ無い（verify-com アプリは ShellLink を 1 個しか作らない）。

分母は 311 のまま、未着手は 7→6 になった。検証済みは 245 のまま。CI 検証は run #8 待ち。テストは 2,124→2,142 件。残る未着手は L14・L15・L16・L18・L19・L20 の 6 件。

### 2026-11-12 02:29 — L14: WinRT の定義は、WinMD から生成できないから手書きの厳選表にする

### 2026-11-12 04:29 — L16: コールバックを「別種のイベント」にするには、WndProc をすり替えるしかない

L16 の文言は「Windows からアプリへ入るコールバックも別種のイベントとして記録する」だ。API 呼び出しのフックでは届かない。コールバックは Windows がアプリの関数を呼ぶ方向で、フックすべき「API 呼び出し」が存在しないからだ。だから WndProc そのものをすり替える。`RegisterClassExW/A` で登録されるクラスプロシージャと、`SetWindowLongPtrW/A (GWLP_WNDPROC)` で差し替えられるプロシージャを Inline Hook で捕捉し、shirusu のラッパーを差し込む。ラッパーが enter/leave を記録してから元のプロシージャを呼ぶ。

すり替えで一番気を使ったのは透明性だ。`RegisterClassEx` にはアプリの構造体そのものではなくコピーを渡す。アプリが渡した構造体を書き換えると、アプリが同じ構造体を使い回したときにラッパーが見えてしまう。`SetWindowLongPtr` の戻り値は、以前のプロシージャがラッパーだった場合は元のプロシージャへ解決して返す。アプリはラッパーの存在を観測しない。`GetWindowLongPtrW/A` はフックしていないため、アプリが現在のプロシージャを読み戻すとラッパーのアドレスが見えるが、その値を `SetWindowLongPtr` へ渡した場合は再利用して二重ラップしない。二重ラップは動くが、1 回のディスパッチで 2 重のコールバックイベントが記録されてしまう。

ラッパーと元のプロシージャの対応づけは、スロット表にした。ラッパー関数は引数だけでは「どの元のプロシージャを呼ぶか」が判別できない。ディスパッチ時の引数（hwnd・msg・wparam・lparam）には、元のプロシージャの情報が無いからだ。だからラッパー関数自体にスロット番号を固定で持たせ、32 件のラッパーをマクロで生成した。COM の vtable 複製と同じ発想だが、こちらは「関数ポインタをすり替える」ための表だ。同じ元のプロシージャは同じスロットを再利用する。スロットが尽きたらラップせず素通しにする。コールバックの記録だけが無く、アプリの動作は変わらない。

WndProc の失敗値には、特に気を使った。元のプロシージャを呼ばずに 0 を返す経路は作らなかった。WndProc が 0 を返すと、WM_NCCREATE / WM_CREATE でのウィンドウ作成の失敗など、アプリの挙動が変わるからだ。ランタイムが無い場合も、スロット表から元のプロシージャを引いて素通しで呼ぶ。記録の都合でアプリを壊してはいけない。

入れ子の仕組みは、作る必要が無かった。コールバック enter を記録して呼出スタックへ積めば、コールバック中の API 呼び出しは A43 / C18 の仕組みで親子として記録される。L15 と同じく、L16 は既存の仕組みの上に薄い層を載せただけの項目だった。コールバックイベントはトップレベル（`parent_call_id == 0`）なので、L15 の再実行規則（トップレベルの呼び出しだけを実行する）にもそのまま従う。

制限は仕様に明記した。検出は WndProc のみで、DialogProc・タイマープロシージャ・列挙コールバックは未対応。`CallbackKind` に種別コードを持たせてあるため、形式を変えずに追加できる。`RegisterClassW/A`・`SetWindowLongW/A`・`GetWindowLongPtrW/A` は未フック。アタッチ前に登録されたクラスはラップされない。

### 2026-11-12 05:29 — L18: Golden の「期待」は、参照 Trace に通るものだけを集めればいい

L18 の文言は「期待値は Windows で毎回取り直す方式と、保存済み Golden を使う方式の両方に対応する」だ。二つの方式は、実は同じ導出の両端だった。参照 Trace から期待ルールを導出する関数が一つあれば、`fresh` はその場で導出して評価し、`record` は導出結果をファイルに書いて `check` が読む。モードの違いは「導出結果を保存するか」だけで、導出の意味は一つにできた。

導出の鍵は、ルールを「作る」のではなく「選ぶ」ことにした点だ。参照に出た API ごとに `api-called` を出すのは作る側だが、`no-integrity-loss` と `object-closed` は、候補のルールを参照 Trace 自身に `evaluate` で probe し、pass したものだけを採用する。参照に損失があれば `no-integrity-loss` は含めないし、閉じていないオブジェクトがあればその `object-closed` は含めない。こうすれば導出ルールは定義上、参照自身にすべて pass する。Golden が参照と矛盾する、という自己矛盾が起きない。`event-count` だけは導出しなかった。呼び出し回数は実行ごとのタイミングで変わりうるので、Golden の期待としては脆すぎる。回数の期待が要る場合は、保存済み Golden の `rules` に手で追加する。

環境情報は、Golden に付けるものであって Trace 形式を変えるものではない、と線を引いた。`os_version`／`os_build`／`cpu_arch` は参照 Trace の `CaptureEnvironment` から取れる。だが `cpu`／`locale`／`gpu` は Trace 形式が持たない。Host に自動収集を載せる手もあったが、Windows 専用コード（CPUID・ロケール・DXGI）を増やす変更で、ローカルでは検証できない。L18 の範囲は Golden の仕組みなので、ここは記録時のフラグ（`--cpu`／`--locale`／`--gpu`）で補うことにし、Host の自動収集は将来の拡張として明記した。指定が無ければ unknown としてキーを省略する。

環境の照合を fail にしなかったのも、同じ線引きだ。Golden の環境と候補の環境が違えば、同じ期待が当てはまらない可能性がある。その可能性を人間に示すのが目的で、判定そのものはルールに任せる。だから照合の結果は警告（note）どまりで、終了コードには影響しない。`cpu`／`locale`／`gpu` は候補 Trace が持たないため照合すらできず、報告書の環境欄に表示するだけにした。
